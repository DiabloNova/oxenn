# 19 — DOC-005: Product and user documentation overstate implementation status without evidence levels

## Source
- Finding ID: `DOC-005`
- Original audit: `ai_tasks/docs-folder-audit.md`
- Status: as stated in the source audit; implementation claims remain subject to source verification

## Problem
Product and user documentation label broad catalogues and workflows as Implemented or verified without distinguishing code presence from tested behavior and from a real customer workflow that is connected to providers, durable, authorized, evidence-backed, and release-ready. Existing audit findings include synthetic Technical SEO data, silent AI mock fallback, fictional/default brand identity, and process-local persistence fallbacks, so module existence alone cannot substantiate operational claims.

## Evidence
- `docs/README.md` says documentation reflects implemented repository state.
- `docs/product/README.md` labels many capabilities Implemented.
- `docs/user-guides/README.md` labels dashboard, analysis, workspace, and billing workflows implemented.
- Related source findings BL-001 through BL-004 identify synthetic/mock/default/process-local behavior.

## Affected files and paths
- `docs/README.md`
- `docs/product/README.md`
- `docs/user-guides/README.md`
- Service, API, route, provider, persistence, and test evidence for each claimed capability.

## Impact
Customers and contributors may mistake a UI route or partial code path for an operational product. This damages trust and can lead to commitments that the system cannot currently fulfill.

## Recommended solution
1. Define a shared product-status vocabulary: documented/planned, code-present, partially verified, test-verified, live-provider connected, durably persisted, and release-ready.
2. Require evidence for each status: source path, tests, provider configuration, persistence path, authorization checks, and known limitations.
3. Revalidate every customer-facing Implemented claim against the actual route/action, service, adapter, persistence behavior, provider mode, and test coverage.
4. Preserve MOCK, LIVE, and HYBRID as explicit modes; never present synthetic output as a live measurement.
5. Update product and user documentation only after source-level findings are reconciled; do not blanket-downgrade or upgrade the catalogue without evidence.
6. Add a documentation review checklist so new feature claims cannot be marked implemented based only on a route or component existing.

## Architecture alignment
The architecture requires evidence provenance, explicit provider modes, durable state, and human-approved actions. Documentation must describe verified capability separately from target architecture.

## Verification criteria
Every status claim has evidence and limitations; mock/demo paths are disclosed; customer-facing docs do not claim live readiness without proof.
