# 076 — TST-004: Privileged-path tests do not verify caller identity or allowed-table restrictions

## Source
- Finding ID: TST-004
- Original audit: ai_tasks/tests-folder-audit.md
- Status: confirmed test-coverage or contract gap as recorded in the tests audit

## Problem
Current tests verify rejection of an unregistered purpose and audit logging, but do not assert that the actual caller matches callerModule or that queries are restricted to allowedTables. System-mode tests show tenant-table queries can succeed but do not prove least-privilege constraints.

## Evidence
Evidence: privileged-paths.test.ts checks unknown purpose and audit; system-mode-bypass.test.ts verifies queries succeed in system mode; neither checks caller/table restrictions.

## Affected files and paths
Privileged-path unit tests, tenant context, system client/query boundary, privileged registry.

## Impact
Tests can pass while registry fields remain descriptive metadata rather than enforced capability restrictions.

## Recommended solution
After implementing enforcement for SRC-002, test wrong caller, unregistered purpose, undeclared table, forbidden operation, missing actor, and system/tenant context confusion. Verify raw SQL cannot bypass restrictions. Test audit records for denied and allowed operations. Do not encode current permissive behavior as expected success.

## Architecture alignment
Privileged infrastructure access must be capability-based and bounded; tests must prove the real boundary rather than successful acquisition of system context.

## Verification criteria
Wrong caller/table/operation is rejected; allowed calls are narrowly scoped; all decisions are auditable.

SRC-002, DOC-007, VER-004
