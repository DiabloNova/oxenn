# 009 — RF-009: Email-provider configuration can select a sender that is documented as non-functional

## Source
- Finding ID: `RF-009`
- Original audit: `ai_tasks/root-files-audit.md`
- Status in source audit: configuration comment claim; implementation behavior requires verification

## Problem
The example environment documentation says that setting a non-empty `EMAIL_PROVIDER` selects `ProductionEmailSender`, which currently throws on send, while disabling the invite-token fallback. If the comment accurately reflects the implementation, enabling the provider before a working sender is configured can make email-dependent workflows fail.

## Evidence
- `.env.example:23-26` describes the provider switch and the throwing sender behavior.
- The root audit deferred source tracing of `src/services/email`, provider selection, callers, and tests.

## Affected files and paths
- `.env.example`
- `src/services/email/**`
- Provider selection and configuration.
- Invitation and email-verification callers and their tests.

## Impact
Workspace invitations, verification messages, or other email-dependent workflows may fail after a seemingly valid environment switch. The audit did not independently establish the runtime behavior, so this finding must be revalidated before implementation.

## Recommended solution
1. Trace the actual provider factory, sender implementation, all send callers, and fallback behavior.
2. Define an explicit provider state: configured and operational, unavailable, or intentionally disabled. A non-empty environment variable alone must not imply readiness.
3. Do not select a sender whose send operation is a placeholder or throws unconditionally.
4. Make provider startup validation fail clearly when a required production sender is not configured.
5. Define safe behavior for invitation/verification workflows when email is unavailable; do not silently claim delivery or rely on an undocumented token fallback.
6. Keep development-only token delivery explicitly marked as development behavior and prevent it from being used as a production substitute.
7. Add contract tests for provider selection, send success, send failure, disabled provider, and invitation lifecycle behavior.

## Architecture alignment
Email is an external integration behind an Oxenn-owned adapter. Provider selection and delivery status must be explicit and observable; external provider availability must not silently mutate workspace membership or verification state.

## Verification criteria
- A configured production provider has a real send implementation.
- Missing or non-operational providers fail clearly before a user workflow claims successful delivery.
- Delivery failure is recorded and recoverable.
- Development fallback behavior is explicit and cannot be mistaken for production email delivery.
- Tests cover the provider contract and all dependent workflows.
