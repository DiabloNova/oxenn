# 046 — SCR-007: env-check uses a partial .env parser that differs from runtime dotenv semantics

## Source
- Finding ID: `SCR-007`
- Original audit: `ai_tasks/scripts-folder-audit.md`
- Status: as recorded in the source audit; dependent behavior remains subject to revalidation

## Problem
The environment checker splits each line at the first equals sign and stores the remainder verbatim. It does not parse quoted values, escapes, `export` prefixes, or multiline values, so it can interpret the same environment file differently from the application's runtime loader.

## Evidence
- `scripts/env-check.ts:66-79` uses a custom line split and stores raw values.
- Quoted/escaped/export/multiline dotenv syntax is not handled.

## Affected files and paths
- `scripts/env-check.ts`
- Runtime environment loader and startup validation.
- CI/build workflows that invoke env-check.

## Impact
The checker can reject valid runtime configuration or validate a string containing quotes that the runtime loader would normalize. This creates inconsistent configuration evidence.

## Recommended solution
1. Trace the application's actual environment-loading order and determine whether env-check runs before or after dotenv loading.
2. Reuse the same dotenv parser/library and semantics as the runtime wherever possible.
3. If a restricted syntax is intentional, publish the accepted grammar and reject unsupported forms explicitly rather than parsing them incorrectly.
4. Avoid overwriting already-loaded environment values unless the documented precedence requires it.
5. Add tests for quoted values, equals signs inside values, escaped characters, export prefixes, comments, empty values, and multiline values.
6. Verify package-script/CI invocation before changing behavior.

## Architecture alignment
Configuration is part of the application boundary. Runtime and validation tools must agree on the same effective environment values, especially for database, provider, and secret settings.

## Verification criteria
The checker and runtime resolve the same test fixtures to the same values; unsupported syntax fails clearly; CI and local commands remain deterministic.
