# 041 — SCR-002: db:push guard does not establish that the target database is disposable

## Source
- Finding ID: `SCR-002`
- Original audit: `ai_tasks/scripts-folder-audit.md`
- Status: as recorded in the source audit; dependent behavior remains subject to revalidation

## Problem
The guard blocks a fixed list of known production URL substrings and accepts operator-provided booleans such as `ALLOW_DB_PUSH=true` and `DISPOSABLE_DB=true`. It checks only the count of rows in `information_schema.tables`, which does not inventory every user object. An empty production database on an unlisted/custom hostname could pass if the environment flags are set.

## Evidence
- `scripts/database/db-push-guard.ts:28-52` checks environment markers.
- `:63-84` blocks a fixed URL substring list.
- `:86-99` accepts two environment booleans.
- `:102-126` checks table count only.

## Affected files and paths
- `scripts/database/db-push-guard.ts`
- `package.json` db:push command wiring.
- Database environment/identity configuration.

## Impact
A destructive schema push could be permitted against an unintended target. The success message overstates the evidence of disposability. The audit does not claim that the command was run against production.

## Recommended solution
1. Replace hostname blacklist logic with a positive allowlist of explicitly provisioned disposable database identities, including expected host, database, and environment identity.
2. Verify identity using independent connection/catalog facts; operator booleans may be an additional approval gate but not proof.
3. Inventory all relevant user objects (tables, sequences, views, materialized views, types, schemas, extensions, and other supported objects) rather than only table count.
4. Fail closed when identity cannot be verified, when unexpected objects exist, or when the target is not explicitly disposable.
5. Trace the actual package-script wiring and all bypass paths before changing the guard.
6. Add tests for custom hostnames, empty production databases, misleading environment flags, non-table objects, and identity mismatch.
7. Never execute db:push against production during verification.

## Architecture alignment
Database mutation is a high-impact action and must be gated by an explicit, verifiable target contract. Human/operator intent alone is not an independent safety guarantee.

## Verification criteria
A non-disposable or ambiguous database is rejected before mutation; all relevant objects are checked; tests prove fail-closed behavior; the success message states exactly what was verified.

The implementation is accepted only when the following checks are covered and pass:
1. **Positive target identity and aliases:** the configured target ID exists in the reviewed registry; the URL host, port, database, and dedicated login role match that registry entry exactly; ambiguous or malformed URLs fail closed; and the target is rejected when it aliases any Workspace runtime/migration or Platform Admin runtime/migration database identity.
2. **Driver-effective connection identity:** connection URL query parameters cannot override host, host address, port, database, role, or TLS policy. Duplicate parameters and unreviewed driver options are rejected. A non-local push target requires hostname-verifying `sslmode=verify-full`.
3. **Independent catalog attestation:** the connected server/database identity matches the reviewed target; the database owner is distinct from the push login; the push login has no inherited/assumable role memberships or privileged grants; the database owner comment matches the reviewed attestation; the extension set is exact; and the complete Drizzle-relevant user-object inventory (schemas, relations, types, and routines) is empty.
4. **Fail-closed behavior:** missing, malformed, conflicting, ambiguous, unexpected, inaccessible, or incomplete catalog results and any connection/query/cleanup failure prevent Drizzle from running. Error output is diagnostic but must not expose connection passwords or other credentials.
5. **Command-path binding:** the supported `db:push` script rejects forwarded CLI arguments, runs catalog checks before invoking Drizzle, supplies the dedicated fixed config, and cleans up its temporary invocation marker. The marker is defense-in-depth against accidental direct use only; it is not authenticated proof against a same-user process. Database/network permissions and credential separation remain the security boundary.
6. **Tests and CI:** URL parsing, alias comparisons, role privileges/memberships, owner/comment, exact extensions, full object inventory, invocation marker file safety, expiry, environment pairing, wrapper argument rejection, redaction, and failure paths are exercised by discovered Vitest tests and repository CI.
7. **Database safety and completion:** no production, persistent, Platform Admin, or reviewed disposable `db:push` target is mutated during verification. Branch CI and a Vercel Preview are not sufficient for `Verified complete`; the PR must be merged and successful post-merge CI must be recorded for the exact resulting `main` merge commit. A live disposable-target push test remains pending until a target is separately provisioned, reviewed, and registered.

## Remediation addendum — 2026-11-14

### Implementation and additional hardening
- The positive disposable-target registry remains intentionally empty because no disposable Workspace database has been provisioned and reviewed. `db:push` therefore remains blocked by default.
- The push URL parser now rejects duplicate query parameters, host/port/database/role overrides, and all unreviewed driver options before passing the URL to `node-postgres`. The only permitted query option is a single `sslmode=verify-full`; this prevents the driver from connecting to a destination or using a TLS mode different from the identity and policy checked by the guard.
- Database URLs used only for alias comparison now use a comparison-only parser. It compares host, port, and database without incorrectly requiring a password or the push target's `sslmode=verify-full` policy. Destination overrides remain ambiguous and fail closed.
- `package.json` now invokes one dedicated `db:push` wrapper. The wrapper rejects every forwarded CLI argument, runs the asynchronous catalog attestation, and then launches Drizzle with a fixed config and no caller-controlled connection/configuration arguments.
- `drizzle.push.config.ts` now refuses to load without a fresh, private, short-lived invocation marker bound to the reviewed target ID and a hash of non-secret connection identity fields (protocol, host, port, database, login role, and TLS mode); the database password is deliberately excluded. The wrapper removes the temporary file after Drizzle exits. This is defense-in-depth against accidental direct config use, not an authenticated proof that the asynchronous guard ran: a same-user local process can fabricate the marker. It must not be treated as a security boundary against an operator with the same local privileges.
- The PostgreSQL role-membership test cases now pass arrays as the test argument, so they exercise the non-empty-membership rejection rather than the malformed-value path.
- Environment validation reports absent paired push settings as missing, validates the target-ID format, tests malformed URLs/IDs, and confirms that db:push-only settings are ignored in migrate mode.

### Verification state and scope
- The first CI attempt exposed a TypeScript error in the new attestation test (`ProcessEnv` requires `NODE_ENV`); the test was corrected in follow-up commit `10243201c482770bb1c0c86c714e1075382dc00d`. Earlier branch CI run [#43457642077](https://github.com/DiabloNova/oxenn/actions/runs/43457642077) passed all three jobs on the then-tested implementation head `216bb2be0b9ec6f8d67e16ef03c274a2f93eccaa`; that historical pass does not validate the later URL/wrapper/test changes. The latest source commit and subsequent documentation-only tracker reconciliation are being validated by current branch CI; exact results are recorded in the dated addendum below.
- No persistent, production, Platform Admin, or reviewed disposable `db:push` target was provisioned, connected, migrated, pushed, or modified by this remediation. The guard's catalog tests use mocked responses. The repository's existing CI Isolation Suite does provision a separate ephemeral PostgreSQL service, applies the normal Workspace migration chain, runs its isolation assertions, and tears the service down within that CI job; this is not a reviewed `db:push` target and the guard does not push to it.
- Platform Admin database connection settings, credentials, schemas, and migration files remain unchanged and separate. Workspace runtime/migration credentials, schemas, and migration history remain unchanged; the Workspace developer `db:push` safety guard, dedicated push config, wrapper command, and environment validation are intentionally changed by this PR.
- The wrapper protects the repository's supported `db:push` path and the dedicated Drizzle push config. As already documented in the source finding, a repository wrapper cannot stop a privileged operator who independently possesses other database credentials from manually invoking the vendor CLI with a different configuration; production credentials must remain unavailable to developer/test processes and disposable credentials must be constrained at the database/network layer.
- The finding remains **Implemented — verification pending**. A green branch CI run and Vercel Preview establish branch-level evidence only. `Verified complete` additionally requires the PR to merge and successful post-merge CI on the exact resulting `main` merge commit. No live disposable target exists, so real-target push validation is intentionally not performed.
