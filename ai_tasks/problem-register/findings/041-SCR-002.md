# 041 — SCR-002: db:push guard does not establish that the target database is disposable

## Source
- Finding ID: `SCR-002`
- Original audit: `ai_tasks/scripts-folder-audit.md`
- Current status: **In progress** on `investigation/041-scr-002-review-2026-11-13`; implementation is not yet verified.

## Problem
The original guard relied on a fixed hostname blacklist, `DATABASE_URL`, operator-provided `ALLOW_DB_PUSH=true` / `DISPOSABLE_DB=true` booleans, and a table count from `information_schema.tables`. Those checks did not establish the positive identity or disposable nature of the target. A custom/unknown host could pass if the environment flags were set, and a missing catalog row was treated as an empty database.

## Current-main revalidation
- Revalidated against `main@a9f22b6f794ee9ff6640fad78b581e51b9e385cf` on 2026-11-13.
- Confirmed: `scripts/database/db-push-guard.ts` still used `DATABASE_URL`, hostname substring exclusions, the two operator booleans, and a table-only inventory.
- Confirmed: `drizzle.config.ts` still supplied a hard-coded local PostgreSQL URL with a privileged `postgres` account when `DATABASE_URL` was absent. This overlaps with RF-004; this SCR-002 change removes that fallback as a necessary bypass-hardening measure, but does not close RF-004's separate acceptance criteria.
- Confirmed: the Platform Admin control plane already has its own database URL variables, Drizzle configuration, dedicated target guard, migration runner, and migration directory. These are independent from the Workspace schema and are intentionally not reconfigured by this finding.
- Repository configuration contains examples/placeholders, but no live database connection was verified or used. No production or other live database was queried.

## Implemented change (verification pending)
1. Added `scripts/database/db-push-targets.ts` as a reviewed positive target registry. It is intentionally empty because no disposable Workspace database is currently provisioned and connected.
2. Reworked `scripts/database/db-push-guard.ts` to require a registered target ID and a dedicated `DB_PUSH_DATABASE_URL`, exact host/port/database/login-role matching, a database comment attestation set by a separate database-owner identity, a distinct database owner, least-privilege role attributes, an exact extension set, and a complete fail-closed inventory of user schemas, relations (including sequences/views/materialized views/foreign tables), custom types, and routines.
3. The guard rejects any target that aliases `DATABASE_URL`, `MIGRATION_DATABASE_URL`, `AUTHENTICATOR_DATABASE_URL`, `PLATFORM_ADMIN_DATABASE_URL`, or `PLATFORM_ADMIN_MIGRATION_DATABASE_URL`. A missing, unregistered, malformed, or ambiguous target is rejected before a database connection is attempted.
4. Added `drizzle.push.config.ts`, restricted to the Workspace schema's `public` schema and bound only to the dedicated push URL. The package `db:push` script runs the asynchronous guard before invoking that configuration. Drizzle's ordinary `drizzle.config.ts` is now schema-only and has no implicit database credentials or local superuser fallback.
5. Updated `.env.example` to leave the dedicated push target values empty and disabled by default; removed the misleading `DISPOSABLE_DB` boolean. Updated environment validation to check the paired push settings when the additional approval flag is enabled.
6. Replaced the prior self-running test script (which was outside Vitest's configured discovery paths) with a Vitest suite under `tests/unit/scripts/database/`, which is discovered by the existing unit-test project.

## Scope boundaries
- This command governs only the disposable Workspace schema-push path. It does not configure or combine the Workspace runtime/migration database with the independent Platform Admin database.
- No database was created, attached, connected, migrated, pushed, or modified.
- No Platform Admin schema, migration, database guard, credentials, or runtime behavior was changed.
- The approved target registry remains empty. Consequently, `db:push` is expected to remain blocked until an independently provisioned disposable target is reviewed and explicitly registered.
- Drizzle Kit supports passing a URL directly through CLI options. Repository wrappers cannot prevent a person who already possesses other database credentials from manually invoking the vendor CLI with those credentials. Production credentials must therefore remain unavailable to developer/test processes, and the push login must be restricted at the database/network layer to its registered disposable target. No such live credential or infrastructure configuration was changed here.

## Verification criteria
- A missing or unregistered target is rejected before opening a connection.
- A target matching either Workspace or Platform Admin database settings is rejected.
- Host, port, database, login role, database-owner attestation, TLS requirements, role privileges, extensions, and user-object inventory must all match the reviewed registry entry.
- Missing catalog rows, malformed catalog values, query/connect/cleanup errors, unexpected objects, and identity mismatches fail closed.
- The test suite is discovered by the unit-test project and executed by CI.
- No production/live database is accessed during verification.
- The success message describes only checks the guard actually performed; it does not claim that it performed a database mutation.
