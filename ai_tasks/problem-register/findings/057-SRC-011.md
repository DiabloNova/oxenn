# 057 — SRC-011: Tenant database transactions remain open during network and AI operations

## Source
- Finding ID: `SRC-011`
- Original audit: `ai_tasks/src-folder-audit.md`
- Status: as recorded in the static source audit; runtime/deployment conditions remain subject to revalidation

## Problem
TenantContextManager holds a database transaction and leased client for the entire callback. Several callbacks perform multi-chunk ingestion, site crawling, or LLM work before completing, so slow external dependencies keep database transactions and connections open.

## Evidence
- `TenantContextManager.runWithTenantContext` begins a transaction and holds the client for the callback (`tenant-context/index.ts:255-343`).
- Document ingestion, premium audit, legacy audit, and competitive analysis callbacks perform external fetch/AI work inside the context.

## Affected files and paths
- TenantContextManager transaction wrapper.
- Document ingestion, audit, and competitive analysis routes/services.
- Repository methods and job orchestration.

## Impact
External provider latency can exhaust the database pool and create long-lived transactions, even when PostgreSQL itself is healthy. This can increase lock duration and reduce throughput.

## Recommended solution
1. Separate external fetch/AI computation from short database transactions.
2. Use a staged workflow: validate/authorize and read required state in a short transaction; perform network/model work outside the transaction; persist results in a new short tenant-scoped transaction.
3. Persist an explicit job/execution state when work must survive retries or exceed request duration.
4. Revalidate tenant membership/authorization before committing results where required.
5. Ensure idempotency and cancellation semantics prevent duplicate writes on retries.
6. Add tests/telemetry for transaction duration, pool release, provider latency, and failure between stages.

## Architecture alignment
The Planning & Execution and AI pipeline layers should orchestrate long-running work without holding persistence transactions open. PostgreSQL transactions should protect only atomic data changes.

## Verification criteria
No external network/model call occurs inside a long-lived tenant transaction; connections are released between stages; result persistence remains tenant-authorized and idempotent.
