# 012 — DB-003: Organization slug has conflicting unconditional and soft-delete-aware uniqueness

## Source
- Finding ID: `DB-003`
- Original audit: `ai_tasks/database-folder-audit.md`
- Status: confirmed schema/behavior inconsistency; desired product policy is unresolved

## Problem
The organization schema declares an unconditional unique constraint on `slug` and also declares a unique partial index on `slug` where `deleted_at IS NULL`. The unconditional constraint means a soft-deleted organization continues to reserve its slug, so the partial index does not provide slug reuse after soft deletion and is redundant for active-row uniqueness.

## Evidence
- `database/schema/organization-table.ts` uses `.unique()` for `slug`.
- The table callback also declares a unique partial index on `slug` with `deleted_at IS NULL`.
- The latest Drizzle snapshot contains both `organizations_slug_unique` and `idx_organizations_slug`.

## Affected files and paths
- `database/schema/organization-table.ts`
- Active Drizzle migrations and snapshots.
- Organization create/rename/restore workflows and their tests.

## Impact
The database behavior may contradict the intended lifecycle for soft-deleted organizations. If slug reuse is expected, creation of a new active organization can fail unexpectedly. If reuse is not expected, the partial index is misleading and redundant. The audit did not determine the intended business policy.

## Recommended solution
1. Obtain an explicit product decision on whether a soft-deleted organization releases its slug, and how restore conflicts are handled.
2. If slugs are reusable, remove the unconditional uniqueness in the canonical schema and add a forward migration that removes the old constraint while retaining the active-row partial unique index.
3. Define restore behavior when another active organization has claimed the old slug; require a conflict response or an explicit rename rather than silently changing identity.
4. If slugs are not reusable, remove the misleading partial index and document the permanent reservation rule.
5. Ensure application-level slug checks are advisory only; the database constraint remains the concurrency-safe authority.
6. Add tests for active duplicates, deleted slug reuse, restore collision, concurrent creation, and rename.
7. Do not generate or apply a migration until the product policy is approved.

## Architecture alignment
Organization identity and workspace boundaries must remain stable and deterministic. Slug policy is a product rule enforced by the canonical database schema, not an incidental frontend validation behavior.

## Verification criteria
- Exactly one database uniqueness strategy matches the approved slug lifecycle.
- Concurrent requests cannot create duplicate active slugs.
- Soft-delete and restore behavior is deterministic and documented.
- Migration and schema snapshots agree.

## Related findings
No separate source finding was identified for the same uniqueness conflict. The policy decision must be recorded before implementation.
