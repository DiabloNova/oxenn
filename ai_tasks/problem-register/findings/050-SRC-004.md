# 050 — SRC-004: PostgreSQL repository reads discard database rows and rely on process-local maps

## Source
- Finding ID: `SRC-004`
- Original audit: `ai_tasks/src-folder-audit.md`
- Status: as recorded in the static source audit; runtime/deployment conditions remain subject to revalidation

## Problem
Several AI-intelligence repositories execute PostgreSQL reads but return data from module-level in-memory maps instead of mapping `res.rows`. BrandRepository is entirely process-local and does not use the PostgreSQL brands table. This makes persisted records invisible after a cold process or on another serverless instance.

## Evidence
- WebsiteRepository reads SQL then returns `db.websites` map matches (`src/features/ai-intelligence/repositories/index.ts:1990-2075`).
- PageRepository follows the same pattern around :2075-2155.
- DiagnosticFindingRepository does not hydrate returned rows around :2880-2977.
- BrandRepository around :538-620 uses `db.brands` only.

## Affected files and paths
- AI-intelligence repository module.
- Canonical Drizzle schema and database row types.
- Brand, website, page, and diagnostic finding domain mappings.

## Impact
Persisted tenant data can disappear from the application's view after process restart or across instances. Callers may seed duplicates or overwrite records; generated IDs can diverge from IDs already stored in PostgreSQL.

## Recommended solution
1. Define explicit row-to-domain and domain-to-row mappers for each repository using the canonical schema types.
2. Make PostgreSQL the production source of truth for reads and writes.
3. Keep in-memory repositories behind an explicit test/demo adapter selected by configuration; never silently fall back in production.
4. Reconcile primary keys, tenant predicates, timestamps, nullable fields, and enum mappings with ARCH-003 before mapping data.
5. Add integration tests that create records, restart/recreate repository instances, and read the same rows from a second process/connection.
6. Ensure persistence failures are returned as failures, not hidden by in-memory success.

## Architecture alignment
The architecture separates domain entities from persistence adapters. PostgreSQL is the durable source of truth; process-local storage is permitted only as an explicit test/demo adapter.

## Verification criteria
Rows returned by PostgreSQL are mapped and returned; data survives process restart; tenant filters are enforced; IDs remain consistent; production cannot silently select memory storage.
