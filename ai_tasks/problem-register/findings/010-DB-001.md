## Problem
Five relationship tables contain a non-null `organization_id` foreign key but have no tenant RLS policy in the canonical Drizzle schema, no policy objects in the latest snapshot, and no ENABLE/FORCE RLS coverage in migration `0005_force_rls.sql`:
- `pages_keywords`
- `pages_topics`
- `pages_entities`
- `keywords_topics`
- `topics_entities`

These are organization-owned relationships, not global reference data. Their missing policies appear to have been lost during schema consolidation; older quarantined definitions contained RLS policies.

## Evidence
- `database/schema/index.ts` defines the five tables with `organization_id`, but their callbacks define keys/indexes without `tenantPolicy("organization_id")`.
- `database/drizzle/0005_force_rls.sql` does not include these tables in its tenant RLS list.
- `database/drizzle/meta/0013_snapshot.json` shows empty policy maps for them.
- Older definitions in `database/schema/_legacy/page.ts` and `database/schema/_legacy/topic.ts` contained protections.
- The bootstrap script grants `app_runtime` default DML privileges on tables created by `app_owner`; the deployed login role still needs verification.

## Affected files and paths
- `database/schema/index.ts`
- `database/drizzle/0005_force_rls.sql`
- The active Drizzle migration journal and latest snapshot.
- Tenant-isolation test inventory and runtime tenant-query guards.

## Impact
The database does not independently enforce organization isolation for these relationship rows. Application filters may reduce exposure but do not replace the database boundary. If the deployed application role can access these tables without another enforced control, cross-organization reads or writes may be possible.

## Recommended solution
1. Confirm the intended ownership contract for each table from its foreign keys and domain relationships; do not infer global ownership from the absence of an RLS policy.
2. Add the tenant policy declarations to the canonical Drizzle schema using the same established policy helper and the correct `organization_id` column.
3. Generate and review a forward-only migration that enables and forces RLS and installs the complete SELECT/INSERT/UPDATE/DELETE policies for all five tables.
4. Ensure policy predicates use the canonical transaction-local tenant context setting and fail closed when it is missing.
5. Update tenant-table inventories, privileged-path metadata, and test reference matrices so ownership, policy declaration, migration coverage, and live verification are represented as separate facts.
6. Add independent two-organization tests for SELECT, INSERT, UPDATE, and DELETE, including attempts to forge another organization's ID.
7. Verify the actual runtime role and grants against a disposable PostgreSQL database before considering the database boundary complete.
8. Do not apply the migration to production as part of documentation work; require a separately approved migration/deployment operation.

## Architecture alignment
This is a foundational organization-isolation invariant. The canonical schema and migration chain must express the same ownership contract; runtime tenant context and repository access must not be treated as substitutes for database enforcement.

## Verification criteria
- All five tables have canonical tenant policies and ENABLE/FORCE RLS migration coverage.
- A fresh database and an upgraded disposable database both reflect the same policy state.
- Cross-organization reads and writes are denied for the runtime role.
- Missing tenant context fails closed.
- Test inventories independently know that these five tables are organization-owned.
