# 30 — GHA-003: Main CI workflow does not declare least-privilege GITHUB_TOKEN permissions

## Source
- Finding ID: `GHA-003`
- Original audit: `ai_tasks/github-folder-audit.md`
- Status: as recorded in the original folder audit; any conditional claims remain subject to revalidation

## Problem
The main CI workflow has no workflow-level or job-level `permissions:` declaration. A run at the audited main commit observed read-only effective permissions, but those permissions currently depend on repository/organization defaults and could broaden later.

## Evidence
- `.github/workflows/ci.yml` has no explicit permissions block.
- `capture-regression-baseline.yml` explicitly uses `contents: read`.
- Run `42181198077` observed Contents/Metadata/Packages read permissions and no write permission.

## Affected files and paths
- `.github/workflows/ci.yml`

## Impact
A future repository-default change could grant more permissions to code executed during pull-request CI than the workflow needs.

## Recommended solution
1. Enumerate every workflow job and the exact GitHub API permissions it requires.
2. Set a restrictive workflow-level default, typically no permissions, then grant only required read permissions at the job that needs them.
3. Confirm whether Packages read is actually needed; do not grant it by assumption.
4. Keep token permissions separate from external secret availability and avoid exposing write-capable credentials to untrusted pull-request code.
5. Run every job and inspect effective permissions to verify least privilege.

## Architecture alignment
CI should be a constrained verification environment. Token permissions must not exceed what is required to test the application.

## Verification criteria
Every job declares or inherits an explicit minimal permission set; the workflow succeeds; effective permissions are verified from a run.
