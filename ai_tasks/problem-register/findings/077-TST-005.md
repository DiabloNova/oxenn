# 077 — TST-005: Tests labeled empty-state validation actually assert database unavailability

## Source
- Finding ID: TST-005
- Original audit: ai_tasks/tests-folder-audit.md
- Status: confirmed test-coverage or contract gap as recorded in the tests audit

## Problem
The tests stub an empty brand/citation repository, call the action, then expect failure with ServiceUnavailable. Their comments say the action fails because the database is unavailable. They do not test a successful known-empty dataset.

## Evidence
Evidence: tests/actions/empty-states.test.ts:25-34 and :36-44 expect success=false and ServiceUnavailable for brand/citation data.

## Affected files and paths
tests/actions/empty-states.test.ts, brand/citation actions and repository contracts.

## Impact
A valid empty workspace can be treated as unavailable; tests do not prove the UI can render a real empty state.

## Recommended solution
Separate three outcomes in domain/API contracts: known empty collection, unavailable source, and measured zero. Update tests so a reachable repository returning [] produces successful empty state; unavailable DB/provider produces explicit unavailable state. Ensure UNKNOWN is not converted to ZERO and no fixture data is silently inserted.

## Architecture alignment
The architecture explicitly preserves UNKNOWN != ZERO. Empty, unavailable, and measured-zero states must remain distinct.

## Verification criteria
Tests independently verify empty success, unavailable failure/degraded state, and measured zero; UI displays each accurately.
