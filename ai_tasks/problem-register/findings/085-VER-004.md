# 085 — VER-004: Privileged-path verification overstates guarantees provided by the registry

## Source
- Finding ID: VER-004
- Original audit: ai_tasks/verification-folder-audit.md
- Status: historical evidence or verification gap as described in the original audit; unsafe probes are not authorized for execution

## Problem
A historical report says runWithSystemContext strictly validates purpose tags against the registry. That establishes a purpose-key check but not callerModule or allowedTables enforcement. Current SRC-002 confirms those fields are not enforced, and TST-004 confirms tests do not assert them.

## Evidence
Evidence: phase-5/j029 describes Object.hasOwn purpose validation; source audit SRC-002 finds caller/table fields unenforced; TST-004 finds missing tests.

## Affected files and paths
Historical phase-5 verification report, privileged registry/runtime query boundary, privileged-path tests.

## Impact
The historical wording can be interpreted as proof of least-privilege even though the runtime only verifies purpose registration.

## Recommended solution
Preserve the historical report but qualify its guarantee. After implementing SRC-002, verify caller identity, purpose, table/operation capability, raw SQL behavior, and audit actor. Update the verification report with exact tests and limitations; do not reuse the old statement as current security evidence.

## Architecture alignment
Privileged access must be enforced by OXENN-owned capabilities and query boundaries, not descriptive registry fields.

## Verification criteria
A current test proves wrong callers, tables, and operations are rejected; historical report is explicitly limited to purpose-key validation.

SRC-002, TST-004
