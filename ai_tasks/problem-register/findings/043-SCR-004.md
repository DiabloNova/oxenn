# 043 — SCR-004: Crawl worker catch suppresses diagnostics even though the orchestrator persists ordinary failures

## Source
- Finding ID: `SCR-004`
- Original audit: `ai_tasks/scripts-folder-audit.md`
- Status: as recorded in the source audit; dependent behavior remains subject to revalidation

## Problem
The worker's catch block keeps polling but does not emit a worker-side diagnostic for the rethrown error. A source cross-check confirmed that the orchestrator already marks ordinary execution failures, publishes `crawl.failed`, and rethrows. The earlier claim that ordinary failures were not persisted is withdrawn; the remaining finding is missing diagnostic context for errors reaching the worker catch, plus unverified failures before/inside the orchestrator's failure-persistence path.

## Evidence
- `scripts/crawl-worker.ts:102-139`, especially empty catch at `:116-136`.
- `src/features/acquisition/application/orchestrator.ts:230-276` catches ordinary failures, marks the job failed, publishes `crawl.failed`, then rethrows.
- The worker was not started.

## Affected files and paths
- `scripts/crawl-worker.ts`
- `src/features/acquisition/application/orchestrator.ts`
- Worker logging/metrics and error correlation.

## Impact
Operators may see a worker loop continue without enough context to diagnose repeated failures. Adding a second failure transition in the worker would be incorrect because the orchestrator already owns ordinary state transitions.

## Recommended solution
1. Keep the orchestrator as the single owner of crawl job lifecycle transitions; do not duplicate failed-state writes in the worker.
2. In the worker catch, emit a sanitized structured log and metric with job/correlation identifiers, error class, retryability, and stage—without secrets or raw sensitive payloads.
3. Distinguish expected cancellation/abort from unexpected worker failure.
4. Add bounded retry/backoff or alerting only according to the existing worker contract; do not silently swallow persistent failures.
5. Separately verify exceptions that occur before the orchestrator's internal try and failures while persisting/publishing the failure state.
6. Keep the missing dispatcher SQL function dependency in DB-004/SRC-015, not in this finding.

## Architecture alignment
The execution orchestrator owns durable state and policy; worker observability should add diagnostics without creating a competing state machine.

## Verification criteria
Ordinary failure state is persisted once by the orchestrator; worker logs provide sanitized diagnostics; cancellation is not misreported; no duplicate transitions occur.
