### Owner decision: final-administrator account deactivation

The owner selected the workspace-closure policy. When account deactivation would leave an active workspace without an active `workspace_admin`, the workspace is soft-deactivated in the same transaction as account deactivation. Its membership rows are retained for audit/recovery, all sessions scoped to that workspace are revoked, and the closed workspace is omitted from workspace lists and cannot receive a new session or accept an invitation. Where another active workspace administrator remains, only the deactivating user's membership and workspace sessions are removed.

For this invariant, an active administrator means a `workspace_admin` membership whose user and organization both have `deleted_at IS NULL`. The operator-only Workspace `super_admin` override remains separate from this customer workspace-admin count.

### Implemented repository behavior

- `removeMemberAction`, `updateMemberRoleAction`, and `inviteUserAction` take a row lock on the active parent organization before changing membership-adjacent state. They re-check the actor's workspace administrator authority after the lock; self-removal and self-demotion are covered. Removing/demoting the final active administrator returns `LAST_WORKSPACE_ADMIN`.
- Account deactivation locks the user row, processes workspaces in deterministic organization-ID order, takes the same organization-row lock before counting active administrators, and atomically closes orphaned workspaces, removes other memberships, revokes sessions, soft-deactivates the account, and writes the audit event. A failed account update throws so the transaction rolls back.
- Workspace listing filters out soft-deactivated workspaces. Invitation acceptance and workspace switching lock and re-check active workspace state. Workspace creation, invitation acceptance, workspace switching, and session creation serialize against account deactivation using the user-row lock. Session creation additionally verifies that the workspace is active and the user still has a membership.
- Removed nested manual transaction boundaries from the membership-removal and workspace-switch actions; they now rely on the transaction already managed by `TenantContextManager`.
- The operator CLI uses a dedicated `sys-grant-super-admin` purpose so it does not rely on the test-only `sys-admin-run` purpose. Its `allowedTables` registry value narrows the tables recorded in audit metadata only; it does **not** enforce SQL table-level access restrictions or change the database connection's privileges.
- Existing schema and migrations are reused; no schema migration was added.

## Problem
Role-change and member-removal actions authorize the acting administrator but do not ensure that another active workspace administrator remains. Concurrent role changes can race unless the invariant is enforced transactionally.

## Evidence
Evidence: updateMemberRoleAction and removeMemberAction in workspace.ts update/delete memberships without protecting the final workspace_admin.

## Affected files and paths
Workspace membership actions/repository, organization membership schema and transaction strategy.

## Impact
A workspace can be left without an administrator and require platform-level intervention.

## Recommended solution
Define the invariant that every active workspace retains at least one active administrator. Enforce it in the same transaction as role change/removal with concurrency-safe locking/serialization. Handle self-demotion, self-removal, concurrent changes, and workspace closure. Return a stable domain error when the last admin would be removed. Test concurrent demotions and revoked memberships.

## Architecture alignment
Workspace RBAC and organization recoverability are server/database invariants, not UI rules.

## Verification criteria
No committed state leaves an active workspace without an administrator; concurrent requests cannot bypass the invariant.
