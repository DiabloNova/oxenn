# 16 — DOC-002: Database security specifications describe incompatible or obsolete RLS coverage

## Source
- Finding ID: `DOC-002`
- Original audit: `ai_tasks/docs-folder-audit.md`
- Status: as stated in the source audit; implementation claims remain subject to source verification

## Problem
The database and security documents do not describe one consistent RLS contract. One specification says exactly 12 tables are isolated; a historical reconciliation report uses an older 51/19 split and classifies every table without a policy as Global/System Context; several current documents claim the 51 policy-bearing tables match all tenant-scoped tables; and one illustrative policy uses `app.current_organization_id` while the canonical contract uses `app.current_tenant_id`. The current snapshot has 70 tables and 51 policy-bearing tables, but that count does not prove every tenant-owned table is protected.

## Evidence
- `docs/architecture/database/tenant-context-spec.md` states a 12-table RLS scope.
- `docs/architecture/database/reconciliation-report.md` contains the older 51/19 classification.
- `docs/security/README.md`, `docs/architecture/README.md`, and MVP Phase 0/1 documents overstate the completeness of the 51-policy set.
- `docs/architecture/features/ARCHITECTURE.md` uses `app.current_organization_id`; the canonical contract uses `app.current_tenant_id`.
- DB-001 establishes five organization-owned tables missing from the policy set.

## Impact
Contributors may rely on obsolete table counts or the wrong tenant-context setting, and reviewers may mistake the existence of 51 policies for proof that all tenant-owned data is protected. Static migrations can also be mistaken for live production state.

## Recommended solution
1. Establish one canonical RLS contract with explicit definitions for organization-owned tables, global/platform tables, and user-owned tables.
2. Publish separate counts for (a) all tenant-owned tables, (b) tables with policy declarations, (c) tables covered by ENABLE/FORCE RLS in the active migration chain, and (d) tables verified against a disposable live PostgreSQL instance.
3. Use the canonical tenant context setting consistently in examples and policy specifications; do not introduce a second setting name.
4. Mark the 12-table specification and historical 51/19 report as superseded, preserving them as historical evidence rather than deleting them.
5. Reconcile claims of complete coverage only after DB-001 and the independent ownership inventory are resolved.
6. Add a documentation consistency check for canonical setting names and stale counts. Never represent repository metadata as proof of production database state.

## Architecture alignment
The security contract must distinguish product/organization ownership, RLS policy definition, migration state, and verified runtime enforcement.

## Verification criteria
All current documents point to one canonical tenant setting and contract; historical counts are labeled; every table is accounted for by ownership and enforcement state; no unsupported production claims remain.
