# 21 — DOC-007: Privileged database path documentation uses legacy tenant tables and stale source paths

## Source
- Finding ID: `DOC-007`
- Original audit: `ai_tasks/docs-folder-audit.md`
- Status: as stated in the source audit; implementation claims remain subject to source verification

## Problem
The privileged database path document lists legacy tables such as `tenants`, `tenant_users`, and `tenant_invitations`, and older source paths. The canonical schema uses `organizations`, `organization_members`, and `organization_invitations`. The repository context also says the privileged-path registry is audit metadata rather than an enforced SQL/table allowlist. Because the document describes privileged system-context access, stale names can misrepresent the actual boundary.

## Evidence
- `docs/security/privileged-paths.md` uses legacy table/path names.
- Canonical schema uses organization-based tables.
- `docs/REPOSITORY_CONTEXT.md` says the registry is metadata and `organization_members.role` is authoritative for workspace role.

## Affected files and paths
- `docs/security/privileged-paths.md`
- `src/core/database/privileged-paths.ts`
- All `runWithSystemContext` call sites and their SQL.

## Impact
Reviewers may believe privileged access is restricted or inventoried when the actual SQL, callers, or tables differ. A documentation list must not be mistaken for an enforced security boundary.

## Recommended solution
1. Compare the document with the current privileged-path registry, all system-context call sites, and the exact SQL executed by each caller.
2. Record caller identity, purpose, required capability, tables/operations, tenant context assumptions, and authorization checks for each path.
3. Distinguish an audit registry from a runtime-enforced allowlist. If enforcement is required by the approved architecture, implement it at the query boundary in a separately approved code change.
4. Replace obsolete table and file names only after the source trace is complete.
5. Add a consistency check that detects stale paths and tables in the published privileged-path document.

## Architecture alignment
Privileged access must be constrained by enforceable OXENN-owned contracts and explicit authorization. Documentation is evidence and explanation, not a security control.

## Verification criteria
Every documented path matches a verified caller and SQL operation; obsolete names are removed; the document clearly states which controls are enforced and which are metadata.
