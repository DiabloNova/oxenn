# 040 — SCR-001: Tenant-table verification and reference-matrix generation equate RLS policy presence with tenant ownership

## Source
- Finding ID: `SCR-001`
- Original audit: `ai_tasks/scripts-folder-audit.md`
- Status: as recorded in the source audit; dependent behavior remains subject to revalidation

## Problem
The tenant-table generator derives the tenant-scoped table set only from snapshot tables that already have one or more RLS policies. The reference-matrix generator then labels a table Tenant-Scoped only if it appears in that policy-derived set; every other table becomes Global. This confuses two separate properties: data ownership and enforcement state.

## Evidence
- `scripts/database/verify-tenant-tables.ts:48-57` derives tables from policy-bearing snapshot entries.
- `verify-tenant-tables.ts:60-73` generates `TENANT_SCOPED_TABLES` from that set.
- `scripts/database/build-reference-matrix.ts:124-128` labels all other tables Global.
- The five tables in DB-001 are organization-owned but lack policies.

## Affected files and paths
- `scripts/database/verify-tenant-tables.ts`
- `scripts/database/build-reference-matrix.ts`
- Generated tenant table inventory and reference matrix.
- Tenant context and repository consumers.

## Impact
The generators can omit the five unprotected tenant-owned junction tables and report a clean match while missing the underlying security defect. This is false assurance, not merely a documentation-label issue.

## Recommended solution
1. Maintain an authoritative ownership inventory independent of policy state, based on the domain contract and explicit table metadata.
2. Report ownership, declared RLS policies, ENABLE/FORCE migration coverage, and runtime verification as separate fields.
3. Make verification fail when any organization-owned table lacks the required policy or migration coverage.
4. Ensure the reference matrix never infers Global solely from absence in the policy-derived set; require an explicit global/platform ownership declaration.
5. Reconcile the five DB-001 tables and add an independent expected-table oracle so the generator cannot validate itself.
6. Keep generator write modes disabled during audit and use disposable database tests for runtime verification.

## Architecture alignment
The tenant-isolation boundary is a core architecture invariant. Ownership metadata must be explicit, and verification must be independent of the mechanism it is intended to verify.

## Verification criteria
The five junction tables are reported as organization-owned; missing policies fail the check; the matrix exposes ownership and enforcement separately; an independent expected inventory catches omissions.
