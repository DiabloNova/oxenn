# 005 — RF-005: Example environment configuration includes privileged local defaults and a predictable placeholder secret

## Source
- Finding ID: `RF-005`
- Original audit: `ai_tasks/root-files-audit.md`
- Status in source audit: potential configuration hazard; no production secret exposure was established

## Problem
The example environment file contains local PostgreSQL connection strings using a superuser-style username/password and a predictable placeholder session secret. The file labels these values as local-development examples and warns against using them in production, but the runtime/deployment validation that enforces those warnings had not yet been verified.

## Evidence
- `.env.example:2-3` uses local `postgres:postgres` connection strings for application and migration URLs.
- `.env.example:9` uses the same style of credentials for `AUTHENTICATOR_DATABASE_URL`.
- `.env.example:5-7` says production must use a dedicated least-privilege login role.
- `.env.example:21` contains the predictable placeholder `change-this-to-a-secure-32-character-secret-in-production`.

## Affected files and paths
- `.env.example`
- `scripts/env-check.ts`
- Runtime session-secret validation.
- Deployment environment configuration and documentation.

## Impact
If copied unchanged into a non-development environment, these values would violate least-privilege and secret-strength expectations. The audit did not establish that these values are used in production; the risk is unsafe configuration reuse unless the application rejects them.

## Recommended solution
1. Keep example credentials explicitly scoped to local development and avoid presenting them as deployable defaults.
2. Add fail-closed validation for every non-development environment: reject known placeholder secrets, weak secrets, and local superuser database defaults.
3. Validate database URLs by environment and role, including a rule that application runtime credentials cannot be PostgreSQL superuser credentials.
4. Keep migrations and runtime access on separately provisioned roles with only the privileges each requires.
5. Ensure deployment documentation describes secret provisioning through the deployment secret manager rather than copying example values.
6. Add automated tests for placeholder secrets, short secrets, local database defaults in production mode, and privileged runtime roles.
7. Do not rotate or claim exposure of any production secret unless separate evidence establishes that it was deployed.

## Architecture alignment
The application, database, and organization security boundaries must be explicit. Example configuration must not weaken the runtime authorization or least-privilege assumptions used by the product architecture.

## Verification criteria
- Production-like modes reject all known placeholders and local privileged defaults.
- Runtime and migration roles are distinct and least-privileged.
- Local development remains usable through an explicitly documented local configuration.
- Tests prove unsafe configurations fail before application startup.
