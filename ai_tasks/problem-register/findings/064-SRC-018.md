# 064 — SRC-018: Email verification is hard-disabled in application code

## Confirmed root cause
The login path previously depended on `REQUIRE_EMAIL_VERIFICATION=false`, making the unverified-account rejection unreachable. Registration also treated verification-mail submission as fire-and-forget, so a new account could be presented as ready even if no sender was configured or the send failed. Existing database-backed sessions were not independently gated by `email_verified_at`, and pre-existing verification tokens were not bound to the account's current email address or to successful message submission.

## Approved product/security policy
For the implemented password-registration path, an account must prove control of its email address before a session can be created or accepted. Registration does not create an authenticated session. After successful verification, the user signs in explicitly. A failed verification-message send leaves the account present but unauthenticated and eligible for a later resend. Public resend responses remain enumeration-safe.

OAuth identity providers, phone OTP, customer onboarding, payments, subscriptions, and paid-service entitlements are separate future implementation scopes; this finding does not claim those capabilities are implemented.

## Implementation
- Removed the hard-disabled verification flag. Password login verifies the password before returning the unverified-email denial, preserving the normal invalid-credentials path for unknown users.
- Enforced `email_verified_at IS NOT NULL` both when creating a database session and when retrieving any existing session. Email verification revokes legacy sessions for the user; the user signs in again after verification.
- Split internal verification delivery from the public resend action. Registration receives an accurate delivery-submission result; public resend keeps a uniform response for unknown, verified, rate-limited, and temporarily undeliverable addresses.
- Added hashed-token lifecycle metadata: current-email snapshot, pending/sent/failed delivery state, sent timestamp, and a sanitized failure code. A verification token can be consumed only after the sender accepts the message, before expiry, and while the current account email still matches its snapshot. The user update must affect exactly one row inside the same transaction as token consumption and session revocation.
- Added a one-hour hashed token, per-email rate limiting, resend supersession only after a replacement email is accepted (a failed resend leaves the previously delivered link usable), strict token-format validation, and an origin-safe HTTPS production link builder.
- Updated registration and verification UI to report initial send failure accurately and send users to login after verification rather than to a dashboard without a session.

## Directly related email dependency
`RF-009` was implemented in the same approved scope because this flow cannot safely require verification while the Production email adapter is a placeholder. The Production adapter now uses Nodemailer SMTP for verification and password-reset messages, validates its settings, enforces TLS, and sanitizes provider errors. The repository has no workspace-invitation acceptance route; therefore invitation email is deliberately unsupported in development and production. The invitation action awaits the sender and revokes a pending invitation when delivery is rejected, rather than returning a broken link or raw token. Implementing the acceptance route remains a separate `SRC-016` scope.

## Database migration
- Added `database/drizzle/0016_email_verification_delivery.sql` and matching Drizzle snapshot/journal metadata.
- Existing tokens intentionally remain unverifiable after migration because they have no email snapshot and retain the default `pending` delivery state; they must be resent.
- The migration is source-only at this checkpoint. No database is connected and no migration was applied.

## Tests added or updated
- Login rejects a correct-password/unverified account and does not create a session; verified login remains supported.
- Registration retains the new account but reports failed verification-message submission and does not create a session.
- Verification requires a sent token bound to the current email, checks the affected-row result, and rolls back if the account cannot be marked verified.
- Session creation/retrieval tests enforce the verified-email condition.
- SMTP configuration, TLS, accepted-recipient semantics, provider failure sanitization, fail-closed unsupported invitation handling, invitation revocation, and safe link construction have contract tests.
