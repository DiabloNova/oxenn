# 042 — SCR-003: Super-admin CLI does not guarantee transaction rollback and connection cleanup

## Source
- Finding ID: `SCR-003`
- Original audit: `ai_tasks/scripts-folder-audit.md`
- Status: as recorded in the source audit; dependent behavior remains subject to revalidation

## Problem
The super-admin grant CLI opens a transaction and performs a role update and audit insert, but does not close the database pool in a guaranteed cleanup path. Failure branches call `process.exit(1)`, and the script has no explicit encompassing `finally` that guarantees rollback and resource release.

## Evidence
- `scripts/auth/grant-super-admin.ts:26-52` opens/commits a transaction but does not close the pool.
- No-membership branch at `:38-42` calls `process.exit(1)`.
- Catch blocks at `:53-61` call `process.exit(1)`.
- Transaction ownership and imported client lifecycle still require verification.

## Affected files and paths
- `scripts/auth/grant-super-admin.ts`
- Database client and system-context transaction helpers.
- Audit logging behavior.

## Impact
The CLI may leave resources open after success and relies on abrupt process termination for failure cleanup. An exception after transaction start lacks an explicit rollback path in the script, making operational behavior harder to reason about.

## Recommended solution
1. Confirm whether the shared database helper owns the transaction or whether the script must manage it directly.
2. Use a transaction API that guarantees rollback on error and release of the acquired connection.
3. Place pool/client cleanup in `finally` and avoid calling `process.exit` while a transaction or resource is active.
4. Set `process.exitCode` only after cleanup completes.
5. Preserve actor attribution, authorization, and audit insertion as one atomic operation.
6. Add tests for success, missing membership, update failure, audit insert failure, rollback, and pool release.

## Architecture alignment
Super-admin actions are privileged, auditable operations. Their state change and audit evidence must be atomic, and resource lifecycle must be deterministic.

## Verification criteria
Every failure rolls back; every path releases the connection/pool; no partial role grant is possible; audit evidence is committed atomically with the grant.
