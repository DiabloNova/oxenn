# 048 — SRC-002: Privileged database path registry is metadata rather than an enforced allowlist

## Source
- Finding ID: `SRC-002`
- Original audit: `ai_tasks/src-folder-audit.md`
- Status: as recorded in the static source audit; runtime/deployment conditions remain subject to revalidation

## Problem
The privileged path registry declares caller modules and allowed tables, but `runWithSystemContext` checks only that a purpose key exists and obtains a system client. The client connection checks only system mode. It does not verify the actual caller or constrain SQL to the declared tables/operations.

## Evidence
- `src/core/database/privileged-paths.ts` defines `callerModule` and `allowedTables`.
- `src/core/database/tenant-context/index.ts:181-215` validates only the purpose key.
- `src/features/admin/infrastructure/persistence/postgres/index.ts:89-108` checks system mode only.

## Affected files and paths
- Privileged path registry.
- TenantContextManager system-context API.
- System database client and all privileged repositories/call sites.

## Impact
Any server-side module able to call the generic system-context API may select a registered purpose and issue SQL against tables outside that purpose's declared scope. The registry therefore implies a least-privilege boundary that is not enforced.

## Recommended solution
1. Inventory all system-context callers, purposes, queries, tables, and operations.
2. Replace generic unrestricted system SQL with narrow purpose-specific repository methods where feasible.
3. If a generic interface remains, enforce capability checks at the query boundary using a non-forgeable server-side capability and structured query metadata; do not rely on TypeScript labels or caller-supplied purpose strings alone.
4. Ensure table/operation allowlists are actually enforced for every query, including raw SQL paths.
5. Keep privileged actor identity, purpose, and affected resources in an immutable audit record.
6. Add negative tests for wrong caller, wrong purpose, undeclared table, forbidden operation, missing actor, and tenant-context confusion.
7. Reconcile the security documentation only after the enforcement behavior is verified.

## Architecture alignment
Privileged operations must be explicitly authorized and auditable. OXENN-owned authorization and repository boundaries—not framework tags or documentation metadata—must decide whether a system query is allowed.

## Verification criteria
A caller cannot exceed its capability; every privileged query is scoped; tests prove wrong-purpose/table/operation calls fail; audit attribution is durable.
