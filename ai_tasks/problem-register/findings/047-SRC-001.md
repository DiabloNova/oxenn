# 047 — SRC-001: Legacy authenticated audit engine has an incomplete SSRF boundary

## Source
- Finding ID: `SRC-001`
- Original audit: `ai_tasks/src-folder-audit.md`
- Status: as recorded in the static source audit; runtime/deployment conditions remain subject to revalidation

## Problem
The authenticated legacy audit route accepts a caller-supplied URL and uses ordinary fetch paths that validate URL syntax/hostname strings but do not resolve and pin DNS answers to approved public IPs. Redirects from crawler, robots, and sitemap requests are not revalidated at every hop. The crawler clears its timeout after headers arrive, before the body is fully consumed, and sitemap text has no size ceiling.

## Evidence
- `src/app/api/v1/audit/engine/route.ts:14-45` accepts the URL.
- `src/lib/audit-engine/url-validator.ts:13-61` does not DNS-pin the connection.
- `crawler.ts`, `extractor.ts`, and `seo-extractor.ts` use ordinary/default redirect-following fetches.
- Newer `src/services/crawler/safe-site-crawler.ts` and acquisition `safe-fetcher.ts` have stronger controls but are not used by this legacy route.

## Affected files and paths
- Legacy audit route, validator, crawler, extractor, SEO extractor.
- Existing safe crawler/fetcher implementations and provider-bound call sites.

## Impact
An authenticated user may cause server-side requests to reach private/internal addresses through DNS rebinding or redirects. Slow/oversized bodies can also hold resources beyond the apparent timeout.

## Recommended solution
1. Route every user-controlled network request through one shared safe-fetch boundary that resolves DNS, rejects private/reserved addresses, pins the validated address for connection, and preserves correct Host/TLS behavior.
2. Revalidate every redirect hop and enforce allowed schemes/ports/content types.
3. Apply one end-to-end deadline and aggregate/per-response byte ceilings through complete body consumption, not just response headers.
4. Migrate the legacy audit route and robots/sitemap fetches to the existing hardened implementation or make the legacy path delegate to it.
5. Ensure redirects cannot bypass validation through provider adapters or secondary resource fetches.
6. Add tests for DNS rebinding, IPv4/IPv6 private ranges, redirects to internal hosts, redirect loops, slow headers/bodies, oversized sitemap responses, and abort propagation.
7. Keep URL policy and transport behavior in one reusable service rather than duplicating validators.

## Architecture alignment
This is a security boundary for externally sourced evidence. The AI assessment pipeline must consume only content fetched through an auditable safe-fetch adapter with bounded resources and provenance.

## Verification criteria
All external fetches use the hardened path; each redirect is checked; private destinations are unreachable; total time/bytes are bounded; tests cover all bypass paths.

## Related findings

## Wave 0 revalidation against pinned main — 2026-11-08

**Disposition:** CONFIRMED — the SSRF boundary remains incomplete in the legacy audit path.

**Baseline:** `main` `7bd2b6ba04e18abbcaf772fac63f29c465a45a42`.

**Current evidence:**
- `src/app/api/v1/audit/engine/route.ts` (blob `a0ff0626f7886326590c7a0852a1ee1a19c6e66b`), lines 10 and 30-36: accepts a caller URL using `z.string().url()` and passes it to `executeAudit`.
- `src/lib/audit-engine/url-validator.ts` (blob `1d8c23455d5c73fc179703217f708cf6dc41b07b`), `isSafeUrl` lines 68-150: performs hostname/IP string checks only; no DNS resolution or address pinning is performed.
- `src/lib/audit-engine/crawler.ts` (blob `12e4d7d92f3deab4c86d26f95fae927cdfdfee5e`), lines 20-50: validates with `isSafeUrl`, then uses native `fetch`; redirects are manual and the next loop iteration repeats only the static check, not DNS pinning.
- `src/lib/audit-engine/extractor.ts` (blob `15c7faf90797fe9cf41edb8f88a6cd053e5cf264`), lines 9-25 and 57-58: robots.txt and sitemap availability use native `fetch` with default redirect behavior after the same static URL check.
- `src/lib/audit-engine/seo-extractor.ts` (blob `4710f5984f69087f98ea94f46febd5f2d4cc6de4`), lines 28-59: sitemap fetch uses native `fetch` with default redirect behavior after static `isSafeUrl`; no redirect-hop DNS validation is visible.
- Hardened alternatives exist (`src/services/crawler/safe-http-fetch.ts`, `src/services/crawler/safe-site-crawler.ts`, and acquisition `safe-fetcher.ts`), but the legacy audit route still uses `executeAudit` and the legacy modules above.

**Tests inspected (not run):** `tests/unit/services/audit-engine/engine.test.ts` covers static private-host checks and redirect-to-private behavior; it does not establish DNS-rebinding resistance. The inspected SEO extractor tests do not establish safe redirect handling for robots/sitemap auxiliary requests.

**Wave 0 conclusion:** The core finding is still valid. Do not mark fixed based on the newer safe crawler, because the legacy route has not been migrated to it. No code or tests were changed or executed.
