# 014 — DB-005: Legacy TableDefinition modules remain beside the canonical Drizzle schema

## Source
- Finding ID: `DB-005`
- Original audit: `ai_tasks/database-folder-audit.md`
- Status: duplicate definitions confirmed; whether any are still imported is unknown

## Problem
The database directory contains a canonical Drizzle schema in `database/schema/index.ts` alongside older `TableDefinition` modules. Some legacy modules remain directly under `database/schema/`, while others are in `database/schema/_legacy/`. The legacy README says the central Drizzle schema is authoritative and prohibits new imports from `_legacy`, but the remaining top-level definitions can still create ambiguity about which schema is current.

The audit did not establish that application code imports these older modules; they must not be deleted solely because they look obsolete.

## Evidence
- `database/schema/_legacy/README.md` identifies `database/schema/index.ts` as the central active schema.
- Older modules remain under `database/schema/`, including citation, competitor, entity, knowledge-graph, metric, observation, and prompt-intelligence definitions.
- The central schema imports/re-exports selected dedicated modules; the complete application import graph was deferred.

## Affected files and paths
- `database/schema/index.ts`
- `database/schema/*.ts` legacy top-level modules.
- `database/schema/_legacy/**`
- Source imports, migration generation, type exports, and tests.

## Impact
Parallel schema definitions can drift and mislead developers or tooling about the canonical table contract. Removing a module without tracing imports could also break runtime behavior or migration tooling.

## Recommended solution
1. Build a complete import/reference graph for every legacy module, including direct imports, barrel exports, scripts, tests, and generated tooling.
2. Compare each legacy definition with the canonical Drizzle table and record whether it is identical, divergent, still consumed, or unused.
3. For active consumers, migrate them to canonical schema types/repositories in bounded changes and add regression tests.
4. For unused modules, move or retain them under a clearly marked historical archive only if there is a documented reason; otherwise remove them in a separately reviewed cleanup after reference checks pass.
5. Enforce a lint/typecheck or architecture test that prevents new imports from the legacy directory.
6. Ensure migration generation and runtime queries import only the canonical schema.
7. Keep this work separate from DB-001 RLS policy changes; shared paths may require coordinated ownership.

## Architecture alignment
The canonical Drizzle schema is the persistence contract for the application. Domain types, repository mappings, and migrations must derive from or be explicitly mapped to that source rather than maintaining parallel table definitions.

## Verification criteria
- Every legacy module has a documented disposition backed by import-graph evidence.
- Active code uses the canonical schema contract.
- No new legacy imports are possible through the agreed static guard.
- Migration generation and runtime typechecking use the canonical schema.
- No file is deleted before proving it has no required consumers.
