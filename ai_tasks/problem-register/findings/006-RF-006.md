# 006 — RF-006: Security-header guidance describes a CSP report-only phase that is not configured

## Source
- Finding ID: `RF-006`
- Original audit: `ai_tasks/root-files-audit.md`
- Status in source audit: confirmed absence in the inspected config; deployment policy remains unverified

## Problem
The security-header configuration comments say Content Security Policy should first be deployed in report-only mode, but the configured response headers do not include either `Content-Security-Policy` or `Content-Security-Policy-Report-Only`. The same configuration enables HSTS with `includeSubDomains; preload` even though the suitability of that policy for every served domain and subdomain had not been established.

## Evidence
- `next.config.ts:5-6` describes a future CSP report-only phase.
- `securityHeaders` contains X-Frame-Options, X-Content-Type-Options, Referrer-Policy, Permissions-Policy, HSTS, and DNS-prefetch control, but no CSP header.
- `next.config.ts:13` enables HSTS with `includeSubDomains; preload`.

## Affected files and paths
- `next.config.ts`
- Actual production and preview domains/subdomains.
- CSP reporting endpoint and frontend resource requirements.
- Security documentation and deployment configuration.

## Impact
The documented hardening step is not active in the inspected config. This is a security-hardening gap, not proof of an exploitable vulnerability. Incorrectly applying HSTS preload to a domain whose subdomains do not support HTTPS could also cause persistent reachability problems.

## Recommended solution
1. Inventory the real production, preview, API, asset, and customer-controlled domains before defining a policy.
2. Derive CSP directives from the actual frontend resource graph, including scripts, styles, fonts, images, frames, API calls, and any required third-party providers.
3. Configure a report-only policy first, with a real and monitored reporting endpoint; do not claim report-only protection if no header is emitted.
4. Analyze reports, remove unsafe dependencies where feasible, and only then consider enforcement with a staged rollout.
5. Verify HSTS coverage and preload eligibility against the actual domain/subdomain ownership and HTTPS deployment state before retaining or changing `includeSubDomains; preload`.
6. Add automated response-header tests for the intended environments and document any deliberate preview/production differences.

## Architecture alignment
The policy must reflect actual provider integrations and frontend dependencies. Do not add broad wildcard allowances that undermine the product's evidence, identity, or data boundaries.

## Verification criteria
- The intended report-only header is present in the environment where monitoring is configured.
- Reports are collected and reviewed before enforcement.
- Enforced CSP is compatible with the real application resource graph.
- HSTS settings are justified by verified domain ownership and HTTPS coverage.
- Header tests cover production and preview configurations.
