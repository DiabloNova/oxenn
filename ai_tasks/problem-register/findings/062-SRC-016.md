# 062 — SRC-016: Workspace invitation links cannot be completed through the application UI

## Source
- Finding ID: SRC-016
- Original audit: ai_tasks/src-folder-audit.md
- Status: as recorded in the static source audit; runtime/provider/database conditions remain subject to revalidation

## Problem
The invitation action creates a link to /en/accept-invite, but no localized accept-invite page exists. Email sending is fire-and-forget and returns success before delivery outcome. Expired invitation status is updated and then an exception is thrown inside the transaction, rolling back the update.

## Evidence
Evidence: workspace.ts creates the missing route; localized route tree has no accept-invite page; send is not awaited; expiry write is rolled back by transaction failure.

## Affected files and paths
Workspace invitation actions, localized route tree, email adapter, invitation repository/schema.

## Impact
Recipients reach a missing page; inviters may see success after failed email delivery; expired invitations can remain pending.

## Recommended solution
Add a localized acceptance page and server action. Await delivery and distinguish queued/delivered/failed/unavailable. Bind one-time token to intended email, workspace, expiry, and membership. Commit expiry as a durable result rather than throwing and rolling it back. Make acceptance idempotent and re-check entitlement/authorization at commit. Test valid, expired, revoked, replayed, wrong-email, provider failure, and concurrent acceptance.

## Phased acceptance criteria

The finding spans two dependent implementation waves. The Wave 2 work is a separately verifiable persistence/expiry milestone, not closure of the full finding.

### Wave 2 — Persistence and expiry milestone
- Invitation records and one-time token metadata are durably persisted and bound to the intended email, workspace, expiry, and membership context.
- Expiry is committed as a durable state/result and is not rolled back by throwing from the same transaction.
- Repository/service tests prove expiry persistence, token invalidation, and safe handling of concurrent/replayed token consumption at the persistence boundary.
- This milestone does not claim that the recipient-facing page or email-delivery workflow is complete.

### Wave 4 — Recipient-facing workflow and final acceptance
- Localized acceptance pages and server actions work in both supported locales.
- Email delivery is awaited and reports queued/delivered/failed/unavailable outcomes accurately.
- Acceptance re-checks intended identity, workspace membership, entitlement, and authorization at commit; token use is idempotent and safe under concurrency.
- End-to-end tests cover valid, expired, revoked, replayed, wrong-email, provider-failure, and concurrent-acceptance cases.

SRC-016 remains open until both wave milestones pass their respective evidence requirements.

## Architecture alignment
Workspace onboarding is a durable, auditable, tenant-scoped human-authorized workflow.

## Verification criteria
Links resolve in both locales; email failures are explicit; expiry persists; token replay and concurrent acceptance are safe.
