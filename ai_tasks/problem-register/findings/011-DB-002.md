# 011 — DB-002: Text-to-UUID tenant migration lacks an in-migration data preflight

## Source
- Finding ID: `DB-002`
- Original audit: `ai_tasks/database-folder-audit.md`
- Status: missing preflight confirmed; validity of existing production data is unknown

## Problem
Migration `0007_goofy_vanisher.sql` converts `tenant_id` from text to UUID using direct casts in `crawl_cache`, `crawl_jobs`, and `crawl_results`, then adds foreign keys to `organizations(id)`. It does not first verify that every existing value is a valid UUID or that each converted value references an existing organization.

## Evidence
- Migration `database/drizzle/0007_goofy_vanisher.sql` uses `USING "tenant_id"::uuid`.
- Migration `0000_reflective_loa.sql` originally creates the relevant columns as text.
- No live database was queried; invalid or orphaned values have not been established.

## Affected files and paths
- `database/drizzle/0007_goofy_vanisher.sql`
- Migration journal and snapshots.
- Any migration preflight/reconciliation tooling and disposable-database migration tests.

## Impact
A populated database containing malformed tenant IDs can fail during the cast. Values that cast successfully but do not identify an existing organization can fail when the foreign key is added. Without a clear preflight, operators may discover the incompatibility only after beginning migration execution.

## Recommended solution
1. Before editing the migration, determine whether it has been applied in any environment and whether the migration is immutable under the project's release policy.
2. For environments where it is still pending, add a preflight that separately detects malformed UUID strings and UUIDs with no matching organization.
3. Define a deterministic reconciliation policy for each invalid/orphaned row: repair from an authoritative mapping, quarantine with an auditable record, or stop and require operator intervention. Never silently coerce or discard tenant ownership.
4. If the migration has already shipped, prefer a new forward migration or an explicit repair procedure rather than rewriting migration history.
5. Make the preflight fail before any destructive or irreversible alteration and report table names/counts without exposing sensitive row data.
6. Test empty, valid, malformed, orphaned, and mixed datasets on disposable PostgreSQL instances.
7. Record migration state, backup/rollback requirements, and exact environment evidence before any production execution.

## Architecture alignment
Organization identity is a security boundary. Migration logic must preserve tenant ownership and data provenance; an unknown tenant mapping must remain an explicit blocking condition rather than being guessed.

## Verification criteria
- Invalid UUIDs and orphaned organization references are detected before conversion.
- Valid datasets migrate successfully and retain exact organization ownership.
- Invalid datasets stop safely with actionable diagnostics.
- No tenant rows are silently reassigned or deleted.
- Tests cover fresh and populated upgrade paths.
