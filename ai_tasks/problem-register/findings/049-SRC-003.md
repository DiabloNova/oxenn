# 049 — SRC-003: Runtime tenant-query detection omits five organization-owned junction tables

## Source
- Finding ID: `SRC-003`
- Original audit: `ai_tasks/src-folder-audit.md`
- Status: as recorded in the static source audit; runtime/deployment conditions remain subject to revalidation

## Problem
The generated tenant-table inventory omits `pages_keywords`, `pages_topics`, `pages_entities`, `keywords_topics`, and `topics_entities`. The generic query guard derives whether a query requires tenant context from this generated list. Database audit DB-001 independently confirms these tables have organization IDs but lack RLS. Current repository call sites reviewed used tenant context and explicit organization predicates, so no direct endpoint exploit was demonstrated.

## Evidence
- `src/core/database/tenant-tables.generated.ts` omits the five tables.
- `isQueryTenantScoped` in `src/core/database/tenant-context/index.ts` uses that list.
- `PostgresClient.query` uses the classification to require tenant context.
- DB-001 confirms missing RLS policies.

## Affected files and paths
- Generated tenant table list.
- TenantContextManager and PostgresClient query guard.
- Canonical schema and generator.

## Impact
Raw SQL against the five tables is not recognized by the generic tenant-query guard. Combined with missing RLS, this weakens defense in depth even though reviewed current call sites included explicit tenant predicates.

## Recommended solution
1. Define table ownership independently of RLS policy presence using an authoritative domain/schema inventory.
2. Generate tenant ownership metadata from that source, not from the set of tables that already have policies.
3. Make the generic query guard fail closed for all tenant-owned tables, including those whose RLS policy is missing.
4. Add an independent completeness test for the five tables and all future organization-owned tables.
5. Coordinate with DB-001 so canonical policies, generated ownership metadata, migration coverage, and tests agree.
6. Keep global/platform tables explicitly classified rather than treating every unlisted table as global.

## Architecture alignment
The tenant boundary is enforced in layers: explicit ownership metadata, tenant-aware repositories/context, and database RLS. A missing layer must be visible as a failure, never converted into a Global classification.

## Verification criteria
All five tables require tenant context; the generated inventory matches an independent ownership oracle; missing RLS is separately reported; cross-tenant tests pass.
