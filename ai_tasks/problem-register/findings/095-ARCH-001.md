# 095 — ARCH-001: Independent service catalog, purchases, entitlements, and usage metering are not represented as one durable commercial model

## Source
- Finding ID: ARCH-001
- Original source: architecture reconciliation and current architecture-aligned remediation specifications
- Status: additional architecture-driven gap recorded separately from the 94 original audit findings

## Problem
The service catalog shows capability cards and pricing tiers, but service authorization is primarily derived from workspace-wide plan state. Workspace plans and usage come from process-local maps/sample values rather than one durable commercial source of truth. SEO, AEO, and GEO are not independently purchasable SKUs, and a visible card does not prove a customer purchased or is entitled to use that service. This is distinct from the customer's own product being assessed.

## Evidence
Evidence: src/services/dashboard-services/index.ts assigns pricingTier; getWorkspacePlan uses process-local workspacePlans; getWorkspaceUsage returns sample values; SubscriptionService reads PostgreSQL; GEO is not modeled as an independent SKU; service card visibility is not a purchase/entitlement contract.

**Evidence qualification:** The presence of a `SubscriptionService` PostgreSQL code path does not establish that OXENN has a connected production/main database or that this path is operational in production. The reviewed repository baseline has no real/main database connected and uses an internal database simulator. Treat PostgreSQL-backed commercial persistence as a target-state requirement, not an existing live capability. No live database was queried for this finding; any future database verification must use an explicitly approved disposable target and must not infer production connectivity from simulator behavior.

## Affected files and paths
Dashboard service catalog, plan/entitlement service, billing schema, usage metering, SEO/AEO/GEO operation boundaries, public API quotas.

## Impact
Customers cannot reliably buy services independently or trust usage/entitlement state. Direct API calls may bypass UI-only service access. Process-local/sample usage is not durable.

## Recommended solution
Define versioned catalog SKUs, subscription items/purchases, server-side entitlements, quota policies, durable atomic usage reservations/consumption, and explicit optional bundle composition. SEO/AEO/GEO must be independently purchasable; bundles cannot be mandatory. Keep customer product profiles separate from OXENN service subscriptions. Use PostgreSQL as one durable source of truth; remove production process-local plans and sample usage. Do not assume payment provider integration: until approved, activation must come from an authorized auditable billing/admin event. Enforce entitlements server-side at every operation.

## Architecture alignment
Commercial catalog and entitlements are cross-cutting platform capabilities supporting Digital Product Assessment and Planning & Execution. They are not AI-framework concerns and must remain OXENN-owned.

## Verification criteria
SEO/AEO/GEO are independent SKUs; bundles are optional/versioned; every protected operation checks durable entitlement; quotas are atomic; customer products and purchased services are separate; no production path uses process-local plans/sample usage.
