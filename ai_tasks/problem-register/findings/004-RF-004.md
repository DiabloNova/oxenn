# 004 — RF-004: Drizzle configuration silently falls back to a local superuser database URL

## Source
- Finding ID: `RF-004`
- Original audit: `ai_tasks/root-files-audit.md`
- Status in source audit: potential risk; reachability through guarded commands was not yet verified

## Problem
The Drizzle configuration substitutes a hard-coded local PostgreSQL URL when `DATABASE_URL` is absent. A database tool can therefore receive a privileged default target instead of failing because the operator did not explicitly configure the intended database.

## Evidence
- `drizzle.config.ts:8` uses `process.env.DATABASE_URL || "postgres://postgres:postgres@localhost:5432/postgres"`.
- The root audit deferred verification of the database push guard, environment validation, and actual Drizzle command usage.

## Affected files and paths
- `drizzle.config.ts`
- `scripts/database/db-push-guard.ts`
- `scripts/env-check.ts`
- Database scripts and CI commands that consume the Drizzle configuration.

## Impact
A missing environment variable can silently redirect a schema or migration command to a local database using a superuser-style account. The practical risk depends on command guards and execution context; the audit did not establish that production data was exposed or that the fallback was reachable in a destructive command.

## Recommended solution
1. Trace every command that loads `drizzle.config.ts` and determine whether it can mutate a database.
2. Verify the guard's target-identity checks, bypass paths, and behavior when `DATABASE_URL` is missing.
3. Remove implicit privileged fallback behavior from mutating database operations. Require an explicit target URL and fail closed if it is absent or invalid.
4. Keep any local-development convenience in a clearly separate, opt-in command that verifies the expected local database identity before use.
5. Ensure the configured role is least-privileged for the operation and is not silently elevated to a PostgreSQL superuser.
6. Add tests proving missing configuration, unexpected host/database identity, and non-disposable targets are rejected before any SQL mutation.
7. Document the distinction between schema generation, migration application, and destructive push operations.

Do not change the fallback until the current guard and migration contract are fully understood; a premature change could break safe local workflows without closing the actual mutation path.

## Architecture alignment
Database configuration must preserve explicit environment and tenant boundaries. No configuration fallback may weaken the database safety gate or change the canonical Drizzle schema as a side effect.

## Verification criteria
- Mutating commands fail before connecting when no explicit database target is supplied.
- Unexpected database identity and privileged-role conditions are rejected.
- A documented local-only path remains explicit and safe if retained.
- Tests cover all guard bypass and failure paths.
- No production database is accessed during verification.
