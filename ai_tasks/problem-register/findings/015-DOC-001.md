# 15 — DOC-001: Tenant-owned junction tables are classified as Global because RLS is missing

## Source
- Finding ID: `DOC-001`
- Original audit: `ai_tasks/docs-folder-audit.md`
- Status: as stated in the source audit; implementation claims remain subject to source verification

## Problem
The Database Reference Matrix classifies `pages_keywords`, `pages_topics`, `pages_entities`, `keywords_topics`, and `topics_entities` as Global because they have no RLS policies. Each table has a non-null `organization_id` and stores relationships between tenant-owned pages, keywords, topics, and entities. The Canonical Data Contract repeats the circular rule that tables absent from the policy-bearing map are Global. This conceals a missing tenant boundary by treating absence of protection as proof of global ownership.

## Evidence
- `docs/database/reference-matrix.md` marks all five tables Global and reports no RLS policies.
- `docs/database/canonical-data-contract.md` defines Global by absence from the policy-bearing tenant table map.
- The canonical schema and active migration omission is independently recorded in `DB-001`.

## Affected files and paths
- `docs/database/reference-matrix.md`
- `docs/database/canonical-data-contract.md`
- Generated ownership/reference-matrix tooling.

## Impact
Documentation consumers and reviewers may believe these tables are intentionally global. Generated scope reports can reproduce the same classification error and obscure a tenant-owned data exposure.

## Recommended solution
1. Define ownership independently from policy existence. The source of ownership must be the domain contract, foreign-key relationships, and explicit table classification—not whether an RLS policy happens to exist.
2. Extend the matrix schema to report separate fields: ownership scope, policy declared, ENABLE/FORCE migration coverage, and runtime enforcement verification.
3. Classify the five relationship tables as organization-owned, while marking their missing policy state as a defect rather than a Global designation.
4. Generate the matrix from the canonical schema/explicit ownership registry and verify it against an independent expected ownership inventory.
5. Regenerate and reconcile the matrix after the DB-001 schema/migration correction; do not claim live enforcement from static metadata.
6. Add tests that fail if a table with an organization foreign key is silently classified Global without an explicit approved exception.

## Architecture alignment
This is a documentation/data-contract finding linked to the organization isolation boundary. It must reflect the canonical ownership model and preserve the distinction between declared policy and verified enforcement.

## Verification criteria
The matrix identifies all five as organization-owned; reports missing RLS as missing; separates schema declarations from migration and live verification; tests prevent this circular classification.
