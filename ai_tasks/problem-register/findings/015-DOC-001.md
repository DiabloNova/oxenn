# 15 — DOC-001: Ownership scope and RLS verification must remain independent

## Source
- Finding ID: `DOC-001`
- Original audit: `ai_tasks/docs-folder-audit.md`
- Status: **Resolved in the investigation branch.** The original five-table Global / missing-RLS observation was already superseded by DB-001 remediation; this follow-up corrects the remaining contract, classifier, and generated reporting ambiguity.

## Revalidated state
The original report described five organization-owned junction tables as Global because their tenant RLS policies were absent. That description is no longer accurate for the current repository state:

- `pages_keywords`
- `pages_topics`
- `pages_entities`
- `keywords_topics`
- `topics_entities`

The current Drizzle declarations apply tenant policies to all five tables. Migration `0014_db_001_join_table_rls.sql` enables and forces RLS and defines SELECT / INSERT / UPDATE / DELETE policies. Migration `0015_db_001_composite_tenant_fks.sql` enforces tenant consistency across junction relationships. Both migrations are recorded in the active Drizzle journal.

This follow-up does not modify those migrations or the database schema. It separates the independent governance facts so a future missing policy cannot cause a tenant-owned table to be reported as Global.

## Implemented changes
1. `verify-tenant-tables.ts` now exposes one canonical ownership classifier. `organizations` is the tenant root; `organization_id` and `tenant_id` are ownership markers. Any Global exception must be explicit and include a non-empty rationale. Policy completeness remains a separate check.
2. `verify-rls-migrations.ts` reuses the same classifier and exports read-only migration coverage for Matrix generation. It checks the final ENABLE / FORCE state in the active journal; it does not inspect a live database.
3. `build-reference-matrix.ts` reports ownership scope, declared policy objects, tenant-policy coverage, checked-in migration coverage, and runtime verification boundary as separate fields. Static generation explicitly does not claim live enforcement.
4. Regression tests cover all five junction tables with absent policies and ensure they remain Tenant-Owned while policy and migration gaps are reported independently.
5. `canonical-data-contract.md` documents the same ownership and verification model. `reference-matrix.md` is regenerated from the canonical snapshot and active migration journal.
6. `scripts/docs-index-generator.ts` and generated `src/lib/docsIndex.ts` retain all five governance dimensions in the searchable Matrix snippet; a regression test protects this downstream documentation contract.

## Verification boundary
- Static unit tests and generators validate repository metadata and classification logic.
- PostgreSQL runtime enforcement is established only by the CI-run isolation suite against ephemeral PostgreSQL.
- No production database was connected to or modified as part of this work.
