# 15 — DOC-001: Ownership scope and RLS verification must remain independent

## Source
- Finding ID: `DOC-001`
- Original audit: `ai_tasks/docs-folder-audit.md`
- Status: the original five-table Global / missing-RLS observation is superseded by the DB-001 remediation now present in the canonical schema and active migration journal; the remaining contract and reporting concern is addressed by this change.

## Revalidated state
The original report described five organization-owned junction tables as Global because their tenant RLS policies were absent. That description is no longer accurate for the current repository state:

- `pages_keywords`
- `pages_topics`
- `pages_entities`
- `keywords_topics`
- `topics_entities`

The current Drizzle declarations apply the established tenant policy helper to all five tables. Migration `0014_db_001_join_table_rls.sql` enables and forces RLS and defines SELECT / INSERT / UPDATE / DELETE policies. Migration `0015_db_001_composite_tenant_fks.sql` enforces tenant consistency across the junction relationships. Both migrations are recorded in the active Drizzle journal. The current Matrix and generated tenant-owned inventory already identify the five tables as Tenant-Owned / Tenant-Scoped.

This repository inspection establishes checked-in schema and migration state only. It does not prove that a production database has applied those migrations or that runtime enforcement has been independently exercised.

## Remaining problem
The canonical data contract and generated reporting must not define ownership by the presence of an RLS policy. The ownership classification must be derived from the canonical schema/domain model: `organizations` is the tenant root, and `organization_id` / `tenant_id` identify organization-owned dependent tables. A missing or incomplete tenant policy is a defect on a Tenant-Owned table, not evidence that the table is Global.

The Reference Matrix must report independent facts:
1. Ownership scope.
2. Declared RLS policy objects and complete SELECT / INSERT / UPDATE / DELETE tenant-policy coverage.
3. ENABLE / FORCE coverage in the checked-in migration journal.
4. Runtime enforcement verification, without inferring it from static files.

## Recommended implementation
1. Use one canonical ownership classifier for tenant inventory verification, migration verification, and Matrix generation.
2. Permit a Global exception for a table with tenant ownership markers only through an explicit, reviewed entry with a non-empty rationale.
3. Generate separate ownership, policy, migration, and runtime-verification fields from the latest snapshot and active migration journal.
4. Keep the runtime status explicit: static generation cannot establish live enforcement; use the PostgreSQL isolation suite for that evidence.
5. Add regression tests proving that all five junction tables remain Tenant-Owned even when their RLS policies are absent, and that a table without tenant markers remains Global without implying tenant-policy coverage.

## Verification criteria
- The five junction tables are always classified as Tenant-Owned based on schema ownership markers, independent of policy presence.
- Policy completeness is reported separately from ownership.
- ENABLE / FORCE migration coverage is derived from the active journal and reported separately.
- Static output never claims live runtime enforcement.
- Regression tests fail if missing policies cause a tenant-owned table to be classified Global.
