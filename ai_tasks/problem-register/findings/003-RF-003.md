# 003 — RF-003: The database Vitest project can pass without discovering any tests

## Source
- Finding ID: `RF-003`
- Original audit: `ai_tasks/root-files-audit.md`
- Status in source audit: confirmed configuration risk; test inventory was deferred to the tests-folder audit

## Problem
The root Vitest configuration and the dedicated database test project both allow a run with no discovered tests to succeed. This makes a green database-test command ambiguous: it can mean the tests passed, or that no database tests ran at all.

## Evidence
- `vitest.config.ts:11` sets root-level `passWithNoTests: true`.
- `vitest.config.ts:28-33` defines the `db` project with `include: ["tests/db/**/*.test.ts"]` and `passWithNoTests: true`.
- The configuration comment describes this as temporary until `tests/db` is seeded.
- Unit and UI projects explicitly set `passWithNoTests: false`.

## Affected files and paths
- `vitest.config.ts`
- `tests/db/**`
- CI workflow commands that select or omit the database project.

## Impact
A test gate can report success without exercising database isolation, migrations, repository behavior, or other intended database contracts. This creates false confidence in changes that depend on database correctness.

## Recommended solution
1. Inventory the intended database test suite and its actual discovery patterns before changing the configuration.
2. Define the database project's required test files and minimum expected suite contract explicitly.
3. Set the database project to fail when zero tests are discovered once its required suite is present; remove the temporary permissive setting rather than relying on a comment.
4. Ensure the CI workflow invokes the intended project and does not silently omit it.
5. Make skipped tests visible as skipped, not passed, and fail the gate when a required suite is entirely skipped.
6. Add a configuration-level regression test or CI guard that deliberately verifies an empty database project exits unsuccessfully.
7. Keep environment-dependent integration tests in a separately named, explicitly gated project so lack of a disposable database cannot masquerade as successful coverage.

## Architecture alignment
Database tests must prove the persistence, tenant-isolation, and provenance contracts used by the application architecture. A green test status is meaningful only when the expected suite was discovered and executed.

## Verification criteria
- An empty required database test project fails.
- CI reports the exact project and number of discovered/executed/skipped tests.
- Required isolation tests run against a verified disposable PostgreSQL target.
- A deliberately empty suite cannot produce a green required check.
