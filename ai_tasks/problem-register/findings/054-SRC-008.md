# 054 — SRC-008: Ingestion fallbacks persist incompatible embeddings and fabricated graph/sentiment data

## Source
- Finding ID: `SRC-008`
- Original audit: `ai_tasks/src-folder-audit.md`
- Status: as recorded in the static source audit; runtime/deployment conditions remain subject to revalidation

## Problem
When provider keys are absent or requests fail, embedding helpers return synthetic vectors from different distributions for document and query embeddings. Graph extraction returns fixed sample entities and sentiment defaults to positive. The ingestion pipeline persists these outputs into tenant knowledge/document records without a reliable mock provenance boundary.

## Evidence
- `embed-client.ts` returns a synthetic 768-dimensional vector near 0.01.
- `query-embedding.ts` returns a different synthetic vector with first dimension ~0.8–0.95.
- `graph-extraction.ts` returns fixed entities; `sentiment-analysis.ts` returns positive default.
- `document-ingestion.ts` persists results from these helpers.

## Affected files and paths
- Embedding, query embedding, graph extraction, sentiment services.
- Document ingestion persistence pipeline.
- Vector schema/model metadata and knowledge graph entities.

## Impact
RAG similarity compares incompatible synthetic spaces; mock values may mix with real vectors; fabricated entities and positive sentiment can pollute customer knowledge graphs and reports.

## Recommended solution
1. Remove production persistence of synthetic embeddings, entities, and sentiment.
2. Use one versioned embedding adapter/configuration for both ingestion and query; enforce exact dimension/model compatibility.
3. Store provider/model/version, mode, and source provenance alongside vectors and extracted facts.
4. On provider failure, fail the ingestion or quarantine an explicit incomplete record; do not substitute fabricated values.
5. If demo mode is retained, isolate its vector namespace and tenant fixture from production retrieval.
6. Add tests for provider outage, mismatched dimensions/models, mixed LIVE/MOCK data, and retrieval isolation.

## Architecture alignment
The Product Evidence Graph and retrieval layer must preserve provenance and model compatibility. Unknown or unavailable evidence must remain UNKNOWN, not be replaced with fabricated content.

## Verification criteria
No mock vector/fact enters production; ingestion and query use the same versioned embedding space; failures are explicit; retrieval excludes demo data.
