# 060 — SRC-014: Audit endpoints can report success after persistence failure and return a mismatched ID

## Source
- Finding ID: SRC-014
- Original audit: ai_tasks/src-folder-audit.md
- Status: as recorded in the static source audit; runtime/provider/database conditions remain subject to revalidation

## Problem
The legacy audit and premium audit routes catch persistence errors but still return successful results. The legacy builder returns a supplied auditId while the database insert creates another UUID, so the returned ID may not identify a stored row.

## Evidence
Evidence: legacy audit route suppresses persistence errors; builder returns the supplied ID; insert creates a different UUID; premium route also hides write failures.

## Affected files and paths
Legacy audit route/builder, premium audit route, audit repository and follow-up lookup.

## Impact
Customers may believe an audit was saved when it was not. Follow-up lookup can fail because response and stored IDs differ.

## Recommended solution
Use one canonical ID from request through insert, events, response, and lookup. Treat required persistence failure as operation failure; if non-persisted output is allowed, return an explicit persisted=false state. Make writes tenant-scoped and idempotent. Add tests for ID consistency, failed writes, retries, and tenant isolation.

## Architecture alignment
Execution output and durable evidence are distinct. A successful analysis is not a saved customer record.

## Verification criteria
Response ID equals stored row ID; failed persistence is never reported as durable success; retries are idempotent.
