# 082 — VER-001: Verification archive mixes historical branches and commits without consistent baseline identity

## Source
- Finding ID: VER-001
- Original audit: ai_tasks/verification-folder-audit.md
- Status: historical evidence or verification gap as described in the original audit; unsafe probes are not authorized for execution

## Problem
The verification archive contains reports from different branches, dates, and commits. Some later reports omit exact commit/date metadata, while historical reports can be read together as if they certify one current state.

## Evidence
Evidence: phase-0 README, phase-0 census, FE-000, J038, OX-102/OX-103, and remediation execution report cite different baselines; OX-102 lacks exact commit and OX-103 lacks date and commit.

## Affected files and paths
verification/** historical reports, report templates, audit governance and new verification output.

## Impact
A reader may combine unrelated historical results into an implied current certification. This undermines evidence provenance and engineering decisions.

## Recommended solution
Preserve historical reports unchanged. Define a verification record template requiring repository/branch, exact commit SHA, architecture/contract version, date/time, environment identity, command, result, skipped tests, artifacts, and limitations. New reports must bind to the exact target commit and never inherit status from a prior branch. Add a check that blocks incomplete provenance fields for current acceptance reports.

## Architecture alignment
Contract & Provenance Gates require traceable, versioned evidence; verification artifacts need the same provenance as product data.

## Verification criteria
Every new current-state report identifies exact commit, branch, environment, commands, result, and limitations; historical artifacts are labeled historical.
