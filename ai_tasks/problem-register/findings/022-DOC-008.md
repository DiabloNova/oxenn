# 22 — DOC-008: Workspace RBAC and platform-administrator RBAC are not clearly separated

## Source
- Finding ID: `DOC-008`
- Original audit: `ai_tasks/docs-folder-audit.md`
- Status: as stated in the source audit; implementation claims remain subject to source verification

## Problem
The Security Model describes three workspace-facing roles (SuperAdmin, WorkspaceAdmin, Viewer), while the RBAC Model describes seven platform-administrator roles (Super Admin, Platform Admin, Security Auditor, Operations, Finance, Support, Read-Only Observer). The documents do not clearly state whether these are two separate authorization domains, how their role authorities differ, or how cross-context escalation is prevented.

## Evidence
- `docs/security/SECURITY_MODEL.md` defines a three-role set.
- `docs/security/RBAC_MODEL.md` defines a seven-role platform-administrator set.
- Canonical workspace membership authority is `organization_members.role`.

## Affected files and paths
- `docs/security/SECURITY_MODEL.md`
- `docs/security/RBAC_MODEL.md`
- `docs/security/README.md`
- Authentication/authorization implementation and tests.

## Impact
Contributors may conflate customer workspace roles with internal platform operations roles, creating unclear permission checks or accidental privilege escalation across contexts.

## Recommended solution
1. Define workspace RBAC and platform-administrator RBAC as separate bounded contexts with separate role authorities, scopes, and permission evaluators.
2. Specify which actions belong to each context and explicitly prohibit implicit mapping or escalation from a workspace role to a platform role.
3. Identify the authoritative persisted role source for each context and the server-side checks required at every boundary.
4. Reconcile documentation with the actual auth middleware, membership queries, admin routes, and tests before changing implementation.
5. Add negative tests proving a workspace administrator cannot obtain platform privileges and a platform role does not silently grant customer workspace membership.

## Architecture alignment
The architecture requires organization-scoped authorization and explicit human/administrative controls. The two role systems must remain distinct unless a deliberate, audited mapping is specified.

## Verification criteria
Role authorities and scopes are unambiguous; source implementation matches; cross-context escalation tests fail closed.
