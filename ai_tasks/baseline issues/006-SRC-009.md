## 8. Verification plan

Verification must test the crawl job as one bounded unit. Per-response limits alone are insufficient: the aggregate budget must be enforced across every response, including concurrent fetches, before excess bytes are retained, parsed, or queued for downstream work. All limits must be resolved from trusted server-side policy and the effective tenant entitlement; caller input may request a stricter policy but must never raise a plan or platform ceiling.

### 8.1 Deterministic contract and unit tests

- **Aggregate byte budget:** use multiple responses whose individual sizes are below the per-response cap but whose combined size exceeds the job cap. Assert that the job stops at the aggregate ceiling, the response that would cross it is not retained or parsed beyond the permitted bytes, and reported usage never exceeds the enforced budget. Cover exact-boundary, one-byte-over, empty, missing, and malformed content-length cases; do not trust `Content-Length` as the sole enforcement mechanism.
- **Streaming and memory bounds:** exercise chunked/streamed bodies and a response without a trustworthy length. Assert that byte accounting occurs while reading and that the implementation does not buffer an unbounded body before checking the limit.
- **Page and request budgets:** test page-count and total-request ceilings independently. Verify duplicate URLs, failed requests, retries, and redirects are accounted for according to one documented counting rule and cannot create an unbounded request loop.
- **Per-response and elapsed-time limits:** verify a single oversized response is rejected even when aggregate budget remains, and that the job deadline is enforced across queue wait, connection, redirects, body transfer, and processing—not reset for each page.
- **Concurrency and races:** run simultaneous responses that collectively cross the aggregate budget. Assert that budget reservation/accounting is atomic, no concurrent worker can overspend the remaining allowance, and the final recorded usage is consistent. Verify the configured concurrency ceiling under load.
- **Origin policy:** by default, only URLs matching the normalized allowed origin are queued and fetched. Permit one narrowly defined canonical upgrade: `http` to `https` for the identical normalized hostname, from the default HTTP port to the default HTTPS port, with no user-info or hostname change. Never permit an HTTPS-to-HTTP downgrade through this exception. Reject all other scheme changes, cross-origin links, deceptive hostnames, user-info tricks, non-default ports, and malformed URLs unless an explicit server-authorized allowlist permits the destination. Test normalization of host casing and default ports.
- **Redirect handling and safe-fetch boundary:** validate every redirect target before following it; enforce redirect-count limits; reject a redirect to a disallowed origin or unsafe address; and ensure each hop uses the shared DNS-pinned safe-fetch boundary. Test the permitted same-host HTTP-to-HTTPS canonical upgrade, reject HTTPS-to-HTTP downgrade and other scheme changes, and include redirect chains that change host, resolve to private/loopback/link-local addresses, or change DNS answers between validation and connection.
- **Server-side policy clamping:** submit caller policies above, below, and at entitlement/platform limits. Assert that the effective policy is computed server-side as the strictest applicable ceiling, caller values cannot elevate limits, and missing/unknown entitlements fail closed or use the explicitly approved safe default.
- **Usage lifecycle and cancellation:** verify usage is reserved atomically before work begins, actual usage is settled on success and failure, and reservations are released/reconciled on cancellation or worker failure. When any hard budget is exhausted, abort outstanding fetches, stop queue admission, prevent further body retention, and record a stable termination reason and measured consumption.

### 8.2 Integration and adversarial tests

Use deterministic local HTTP fixtures and controlled DNS/network mocks; do not depend on arbitrary public websites. ## 9. Acceptance criteria

- A per-job aggregate byte ceiling is enforced across all responses and concurrent workers before bytes beyond the remaining allowance are retained or processed; per-response limits remain independently enforced.
- Page, total-request, elapsed-time, redirect, and concurrency ceilings are enforced for the whole job, with documented accounting semantics for retries, redirects, failures, and duplicate URLs.
- Same-origin crawling is the default. A same-host HTTP-to-HTTPS upgrade is permitted only between the default ports and only after the destination passes the shared DNS-pinned safe-fetch checks; HTTPS-to-HTTP downgrade is rejected. Other cross-origin crawling is possible only through an explicit server-authorized allowlist; every discovered URL and redirect is revalidated through the shared safe-fetch boundary.
- Effective crawl policy is derived and clamped server-side against tenant entitlements and platform hard limits. Caller-supplied values cannot increase any ceiling.
- Usage reservation and settlement are race-safe and auditable. Exhausting a hard limit cancels outstanding work, prevents further queue admission/body retention, and records a stable reason and actual usage.
- Focused automated tests cover boundary values, aggregate overspend, streaming bodies, concurrency races, origin/redirect bypasses, policy tampering, cancellation, and reservation/settlement failures using deterministic isolated fixtures.
- SRC-009 has its own acceptance evidence for aggregate budgets, concurrency, entitlements, and usage accounting; shared SRC-001 safe-fetch coverage is cross-referenced but does not replace these checks.
- All behavior is revalidated against the current implementation and matches the approved architecture; no historical audit assumption is represented as a confirmed current defect without evidence.
- Documentation and UI claims match the verified implementation state. The change remains bounded to the approved scope and introduces no unrelated product, schema, or deployment changes.
- All original IDs remain traceable and receive an explicit final disposition. Any remaining limitation is documented; no unsupported LIVE/VERIFIED claim is made.
