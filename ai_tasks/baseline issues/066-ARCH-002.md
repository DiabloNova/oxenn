# Architecture Gap ARCH-002 — Current AI runtime does not yet implement the approved LangChain interim boundary

**Type:** New architecture-driven gap discovered during the 2026-11-07 architecture reconciliation  
**Priority:** P2 — AI runtime architecture and migration readiness  
**Disposition:** ARCHITECTURE GAP — introduce incrementally behind an OXENN-owned adapter  
**Evidence baseline:** `DiabloNova/oxenn@7bd2b6ba04e18abbcaf772fac63f29c465a45a42`  
**Architecture baseline:** `docs/architecture/OXENN_PRODUCT_ARCHITECTURE.md`

## 1. Problem and evidence

The previous repository review found `package.json` and the lockfile using the Vercel AI SDK and `@ai-sdk/google`. LangChain was not present in the inspected dependency manifest. Existing AI provider paths also include direct provider selection and mock fallback behavior, including the paths recorded in `SRC-007`, `SRC-008`, and `SRC-005`.

The user has since approved using LangChain as the interim implementation framework until SCRS is operational. This is a target-architecture gap, not evidence that the current application is broken solely because LangChain is absent.

## 2. Architecture mapping

- AI Intelligence Pipeline.
- Deterministic Reasoning Orchestrator.
- LLM Provider Adapter.
- Contract & Provenance Gates.
- Telemetry & Evaluation.
- Decision & Execution Engine.

## 3. Root cause

Current model access and provider selection are not yet demonstrably organized behind the stable OXENN-owned runtime boundary required by the revised architecture. Introducing LangChain directly into domain services would create a new coupling rather than solve the boundary problem.

## 4. Recommended remediation

1. Define an OXENN-owned TypeScript interface for model/runtime requests and structured responses. The interface must include task identity, contract version, product/workspace/market scope, provider/model selection, mode, trace identifiers, usage/cost metadata, and typed failures.
2. Implement LangChain as one adapter behind that interface. Keep LangChain classes and types inside the adapter implementation.
3. Route model access through the adapter; do not allow feature modules to instantiate provider clients directly.
4. Keep workflow state, retries, permissions, approvals, quotas, business rules, and execution ownership inside OXENN.
5. Make LIVE, MOCK, and HYBRID explicit modes. Production must not silently fall back to mock behavior when a provider or credential is unavailable.
6. Preserve provider/model/version, latency, token/cost, error, and trace metadata without indiscriminately logging prompts, customer content, or secrets.
7. Migrate existing workflows incrementally. Do not remove Vercel AI SDK or current provider code until all consumers are identified and an equivalent supported path is verified.
8. Evaluate LangGraph only if a real multi-step orchestration need exists; it must not own durable business state or approval semantics.
9. Keep SCRS as a later, evidence-gated replacement candidate. Compare it with the interim adapter on representative OXENN workloads before migrating. Do not assume a Python runtime or a fixed seven-stage graph.

Use Context7 and the current official LangChain documentation when implementation begins to confirm the installed version's supported APIs. Do not write version-specific code based only on memory or examples from older releases.

## 5. Dependencies and implementation order

- Reconcile with Finding 005 (`SRC-005` through `SRC-007`) to prevent mock output from being represented as live measurements.
- Reconcile with Finding 028 (`SRC-008`) for embedding and ingestion provenance.
- Reconcile with Finding 014 (`SRC-020`) for execution-state correctness.
- Reconcile with Finding 042 (`SRC-019`) before treating scheduled workflows as durable background execution.
- Define and test the OXENN adapter contract before introducing LangChain-specific code into any feature module.

## 6. Risks and rejected approaches

- Do not make LangChain the owner of OXENN domain logic, durable state, permissions, billing, or approvals.
- Do not expose LangChain types in domain contracts.
- Do not create a second Python runtime as a prerequisite.
- Do not copy SCRS's internal execution graph without evidence.
- Do not let a successful model call authorize an external action.
- Do not remove existing AI SDK dependencies before tracing all consumers and validating the replacement.

## 7. Verification plan

- Contract tests for the OXENN runtime interface independent of LangChain.
- Adapter integration tests for valid structured output, provider errors, timeouts, retries, and usage metadata.
- Tests for explicit LIVE/MOCK/HYBRID behavior and production fail-closed provider selection.
- Provenance tests linking each accepted output to source evidence, provider, model, version, and contract version.
- Regression tests comparing existing AEO/SEO workflows before and after adapter routing.
- Evaluation fixtures comparing output quality, evidence integrity, latency, cost, and failure behavior.
- Dependency and lockfile verification for the exact selected LangChain package versions.

## 8. Acceptance criteria

- All model calls pass through the OXENN-owned runtime/provider interface.
- No domain or business module imports LangChain-specific classes or types.
- LIVE/MOCK/HYBRID modes and provider failures are explicit and testable.
- LLM output cannot bypass contract/provenance validation, authorization, entitlements, or approvals.
- Existing workflows remain behaviorally compatible during incremental migration.
- SCRS is not activated until the agreed real-workload evaluation gate passes.

**Implementation status:** NOT STARTED. This is a new architecture adoption plan, not a claim that LangChain has been added or that SCRS is production-ready.
