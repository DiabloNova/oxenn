# J-036: Public API activation: E2E keys, timing-safe compare, atomic quota, persistent rate limit

## Implementation Summary

This phase completes the Public API authentication and rate-limiting productionalization.
The API keys logic was hardened using `crypto.timingSafeEqual` and generating explicit byte buffer lengths for digest comparison. The CLI tooling was implemented with `scripts/api/issue-key.ts` and `scripts/api/revoke-key.ts` explicitly registered into `src/core/database/privileged-paths.ts`.

## Upstash adapter design and fixed-window semantics

The Upstash Rate Limit Adapter (`UpstashRateLimitStore`) leverages standard REST `fetch()` and avoids Upstash SDK dependencies.
It implements Fixed-Window limit semantics leveraging Redis pipelining:
1. `INCR ratelimit:<tenantId>:<windowId>`
2. `EXPIRE ratelimit:<tenantId>:<windowId> <windowSecs> NX`

The integration gracefully falls back to the existing `InMemoryCacheStore` in local and testing environments and fails closed by returning a 429 semantic on connection failure or misconfiguration in production mode.

## Privileged key-issuance path

Two CLI scripts were successfully authored and validated.
- `scripts/api/issue-key.ts`: issues a key and prints raw secret once. Registers via `api-key-issue`.
- `scripts/api/revoke-key.ts`: revokes by key id across tenant boundaries. Registers via `api-key-revoke`.
Both leverage `TenantContextManager.runWithSystemContext` using securely registered privileges in `src/core/database/privileged-paths.ts`.

## Atomic Quota Implementation

The API-Quota verification previously employed a susceptible read-then-write pattern creating potential race conditions under high concurrent usage.
Replaced with a singular deterministic `UPDATE ... RETURNING` query block checking both usage boundaries and updating in a single pass. Zero returned rows cascade to trigger a 'Usage Limit Exceeded' exception enforcing strong integrity against limits.

## Concurrency Test Results
The atomic constraint enforced by PostgreSQL correctly prevented race conditions during the concurrently issued usage tests (`tests/features/public-api/public-api.test.ts`). For a limit of 1000 and 100 pre-used, initiating 11 concurrent consumption requests successfully blocked two requests with a 403 / "USAGE_LIMIT_EXCEEDED" while 9 requests safely passed without violating the 1000 total token allowance.

## API contract notes
The API handles authorization headers safely and transparently exposes 401 statuses for improperly formatted, unregistered, or revoked credentials.
API rate limit exhaustion predictably halts further invocations with a `429` status while appropriately emitting `Retry-After` and `X-RateLimit-Remaining` headers.
