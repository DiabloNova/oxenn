# J-034: Account Deactivation / Deletion Lifecycle

## Implementation Summary
Implemented `deactivateAccountAction(password)` within `src/app/actions/account.ts` alongside unit tests in `tests/unit/app/actions/account.test.ts` and `auth-deactivated.test.ts`. Updated the user profile page to include a "Danger Zone" block for account deactivation.

## Organization / Membership Semantics Evidence
Organizations manage workspaces where users collaborate under a unified billing entity and query quotas. From inspecting existing code (`src/app/actions/workspace.ts` and `src/services/auth/authorization.ts`):
- `organization_members.role` controls access rights (`super_admin`, `workspace_admin`, `viewer`).
- Workspace administrators (`workspace_admin`) manage workspace configuration and other members.
- Removing a member invokes a hard-delete (`db.delete(organizationMembers)`) inside the `ctx-remove-member` context.
- There is currently no pre-existing infrastructure or canonical approach for organization ownership transfer or automatic workspace archival if the last admin departs.

## Exact Account-Deactivation Lifecycle
1. Retrieve active user session (`requireSession`).
2. Verify user password securely using `verifyPassword`.
3. Locate all current workspace memberships across the platform.
4. Process consequences for each organization membership:
    - If another active `workspace_admin` exists, remove the user's membership.
    - If the user is the sole administrator, skip modification.
5. Soft-delete the user via `users.deleted_at = NOW()`.
6. Terminate all active sessions via canonical `revokeAllForUser`.

## Transaction Boundaries
1. **Password Verification:** Executed inside a read-only query in `sys-login` context.
2. **Membership Deletion:** Wrapped in a dedicated PostgreSQL `BEGIN`/`COMMIT` block executed within `runWithTenantContext("ctx-remove-member")` for each organization.
3. **User Soft Deletion:** Written safely within a `sys-login` context.
4. **Session Revocation:** Triggered separately out-of-band by the `revokeAllForUser` service function logic.
The membership adjustments, user soft deletion, and session revocation queries each run within their respective boundaries to honor existing transaction patterns safely instead of artificially joining contexts.

## Exact Session-Revocation Behavior
Called `revokeAllForUser(userId)` from `src/services/auth/session.ts` which executes `UPDATE sessions SET revoked_at = NOW() WHERE user_id = $1 AND revoked_at IS NULL` under the `sys-login` context.

## RLS/System Context Mechanisms Used
- `sys-login`: Reused to verify the user password (allowed table: `user_credentials`) and to execute the final soft-delete (`UPDATE users SET deleted_at = NOW()`).
- `sys-list-workspaces`: Reused to locate the user's active cross-tenant roles/memberships (allowed tables: `tenants`, `tenant_users`).
- `ctx-remove-member`: Safely scoped `runWithTenantContext` to modify tenant-level entries (like `organization_members`) ensuring RLS is respected natively.

All utilized purpose tags and DB execution paths are predefined and natively support the queried DB targets. No custom tags or paths were created.

## Organization Behavior
- **Another Valid Administrator:** Executes existing deletion pattern (`db.delete(organizationMembers)`) to gracefully exit the workspace context.
- **Sole Administrator:** Rejects deletion of the sole admin role. Logs a warning `[J-034]` and safely persists the organization & membership un-archived in the database as a deliberate unaddressed product behavior to avoid unauthorized logic invention.

## Audit Behavior
Leverages `TenantContextManager` automatic lease-based auditing (`privileged_db_access` logs). Additionally, explicitly records an `account-deactivation` event in the `audit_records` table, capturing the specific logical action with the user's role and email to satisfy the explicit event requirement using existing vocabulary tables.

## Authentication Behavior for Deleted Users
Validated by regression test `auth-deactivated.test.ts`:
- The existing login action (`loginAction`) uses `SELECT * FROM users WHERE lower(email) = $1 AND deleted_at IS NULL` to retrieve the active user profile, naturally failing credentials for soft-deleted profiles.

## Email Re-registration Behavior
Validated by regression test `auth-deactivated.test.ts`:
- The existing registration action (`registerAction`) uses `SELECT id FROM users WHERE lower(email) = $1` which identifies the soft-deleted user (not checking `deleted_at IS NULL`) and surfaces `USER_EXISTS` block accurately.

## Unresolved Product / Architecture Decisions
- **Sole Administrator Deactivation:** There remains no structural system instruction dictating what happens when the final administrator of an organization deletes their account. Until defined, J-034 skips deleting their membership, rendering the workspace theoretically abandoned but intact within DB.
