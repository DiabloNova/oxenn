# J-028 Implementation Report: System Context Database Leases

## Mechanism Description

The `TenantContextManager.runWithSystemContext` method has been extended to lease a privileged database connection, mirroring the architecture of `runWithTenantContext`. It now guarantees that any action executing under system mode has a database client (`dbClient`) attached to the transaction context.

The lifecycle looks like:
1. `runWithSystemContext` leases a client from `PostgresClient.connectSystemClient(purpose)`.
2. Starts a `BEGIN` transaction.
3. Executes the callback.
4. Concludes with a `COMMIT` (or `ROLLBACK` on error).
5. Exposes the leased client via `getDbClient()`, fixing the issue where system callers were failing due to missing DB context.

## Role & Connection Matrix

To support differential capabilities, the `PostgresClient` instance now manages two connection pools:
1. **Application Runtime** (from `DATABASE_URL`): Used for regular tenant-bound execution. Tenant contexts lease from this pool.
2. **Authenticator/System Runtime** (from `AUTHENTICATOR_DATABASE_URL` or falling back to `DATABASE_URL`): Provides the privileged role required to access `FORCE RLS` tables without establishing a current `tenant_id`. Used explicitly by `connectSystemClient()`.

## Semantic Adjustments & Callers

* `runWithSystemContext` signature changed to `(userId: string | null, purpose: string, work: () => Promise<T>)`.
* Caller sites now must specify a semantic `purpose` tag indicating *why* system context is invoked (e.g., `"sys-login"`, `"sys-auth-check"`, `"sys-create-workspace"`).
* This explicitly enables upcoming audit logging tasks (`J-029`) by propagating intention through the connection context.
* Unit tests invoking `runWithSystemContext` have been upgraded to match the new `(userId, purpose, work)` signature.
