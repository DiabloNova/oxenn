# Verification Report for J-032 (Email Verification & Reset Delivery)

## Goal
Implement persisted, single-use tokens for email verification and password reset; deliver invitation emails via existing mechanisms, all using a provider-agnostic `EmailSender`. Provide a secure, atomic flow without returning raw tokens.

## Token Policy

| Purpose          | TTL              | Single-use | Storage                         | Raw token returned |
|------------------|------------------|------------|---------------------------------|--------------------|
| Verification     | 24h              | Yes        | SHA-256 only (`email_verification_tokens`) | Never              |
| Password reset   | 1h               | Yes        | SHA-256 only (`password_reset_tokens`) | Never              |
| Invitation       | 24h (Existing)   | Yes        | Existing `organization_invitations` | Never              |

## Verification Gates & Flags
- `REQUIRE_EMAIL_VERIFICATION = false` is defined.
- Existing login behavior allows unverified users when false, but provides a solid enforcement point when toggled.

## Invitation Model
- The existing `organization_invitations` table was **reused**. No parallel table was introduced.
- Existing URL delivery uses `EmailSender` without altering acceptance cryptography.

## Privileged Context / Database Migration
- Verified that J-030/J-031 use `PRIVILEGED_PATHS_REGISTRY` to perform auth operations globally via `runWithSystemContext`.
- New tables (`email_verification_tokens`, `password_reset_tokens`) were added to the allowed tables array for `sys-login` and `sys-register`.
- Migration generated via `pnpm db:generate`.

## Rate Limit Investigation
- Investigated codebase. There is no dedicated rate-limiting middleware or abstraction for public endpoints identified (like upstash or redis sliding windows).
- **Gap:** Native rate limiting is currently missing for `requestPasswordReset` and `requestVerification`. This must be addressed in a follow-up.
- However, atomic failures (e.g., login failure lockouts) already exist.

2. Initialize Resend/SendGrid using `process.env.EMAIL_PROVIDER` credentials.
3. Ensure the error thrown on missing credentials remains.
