# Verification Report for J-033

## 1. DB-Backed Rate Limiting Infrastructure
- Reused standard Drizzle PG setup. Added `auth_rate_limits` table:
  - `endpoint` (text, not null)
  - `bucketKey` (text, not null)
  - `attempts` (integer, default 1, not null)
  - `expiresAt` (timestamp, not null)
- Matches conventions using strict index on `expiresAt` and composite primary key `(endpoint, bucketKey)`.
- Avoided unnecessary random UUID primary key since the composite PK correctly represents identity.
- Enforced an atomic upsert operation logic via `INSERT ... ON CONFLICT ... DO UPDATE`. The query resets the counter if `expires_at <= NOW()` and increments it otherwise, establishing atomic enforcement in a single statement.
- Fail-Closed: any exceptions from `auth_rate_limits` will naturally throw out of the `enforceRateLimit` helper, denying the auth operation outright. Tested to confirm the "fail-closed" security requirement.

## 2. Bucket-Key & IP Limitation Strategy
- The repository Next.js configuration currently lacks an established mechanism for extracting trusted IPs from headers (like `X-Forwarded-For`) within `Server Actions` dynamically via `headers()`.
- To avoid arbitrarily trusting client-controlled headers (which can be spoofed) and per instructions not to invent an ad-hoc proxy extraction mechanism, **IP addresses are NOT used in the rate limiter**.
- **Resulting Bucket Keys:**
  - `loginAction`: Normalized, trimmed email (`login:username@example.com`).
  - `registerAction`: Normalized, trimmed email (`register:username@example.com`). This limits one email from trying to repeatedly sign up but acts strictly as a spam guard, since a global attacker could randomize emails.
  - `requestPasswordReset`: Normalized, trimmed email (`reset:username@example.com`).
- Thresholds:
  - Login: 10 attempts / 15 mins.
  - Register: 5 attempts / 60 mins.
  - Password Reset: 5 attempts / 60 mins.

## 3. RBAC Single Source & `super_admin` Clarification
- Discarded use of `session.user.role` (which contains `role_snapshot` from DB) across `src/services/auth/authorization.ts` (e.g. `requireRole`, `requireWorkspaceMembership`).
  - Note: `CacheService.validateTenantContext` currently still uses `session.user.role`. Refactoring this remaining authorization path will be done in a separate PR to keep this scope focused on primary RBAC definitions.
- Traced `session.user.role` population to active workspace role fetching in `src/app/actions/workspace.ts` which confirmed that `super_admin` privileges are globally granted if the user holds `super_admin` in their currently active workspace context.
- Implemented db-only fetch in `requireWorkspaceMembership` to check the `super_admin` membership of `session.user.workspaceId`.
- In `requireRole`, similarly queries active workspace for `super_admin` bypass or `targetWorkspaceId` if defined.

## 4. `super_admin` Assignment Path
- Verified that application flow (`updateMemberRoleAction`, `inviteUserAction`) currently accepts any role string. This means workspace admins could technically assign `super_admin` through the UI if the client permitted it. This requires a dedicated restriction patch in the application role management paths before certifying `super_admin` is fully operator-only. For now, the database logic only natively inserts via the new operator script.
- Implemented `scripts/auth/grant-super-admin.ts` CLI exactly mirroring `J-009` privileged script norms (`PostgresClient.connectSystemClient("sys-admin-run")`) with standard `process.argv` execution argument structure.
- Writes atomically to `organization_members` and logs an `audit_records` event, strictly using correct table schemas for the audit record.

## 5. Frozen Tables
- Left `roles` and `permissions` untouched, but marked in their schema definition comments as `FROZEN-LEGACY: roles and permissions tables are no longer used for authorization decisions.`.

## 6. Testing Results
- Unit tests run under `vitest` pass, successfully verifying auth limits deny at thresholds and fail securely when the database is unreachable.
- Included regression testing checking database-role lookups dynamically (proving `requireRole` queries DB rather than trusting the function mock input).
- Tested CLI via strict typescript type checking of its database structures.
